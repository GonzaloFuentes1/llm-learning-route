Serving con vLLM: primeros pasos

De cero a un endpoint OpenAI-compatible con vLLM: qué hace PagedAttention, instalación vigente, vllm serve con los flags que importan, cliente con streaming, inferencia offline en batch, métricas en /metrics y un primer benchmark con vllm bench serve usando prompts reales en español y portugués.

1. Qué es vLLM y por qué es rápido

Generar texto tiene dos fases: el prefill (procesar todo el prompt de una vez, limitado por cómputo) y el decode (un token por paso, limitado por ancho de banda de memoria). En cada paso el modelo relee el KV cache de todos los tokens anteriores, así que la VRAM disponible para ese cache decide cuántas conversaciones puedes atender a la vez.

Un generate() ingenuo reserva para cada request un bloque contiguo del largo máximo y procesa un batch fijo hasta que termina el más lento. vLLM cambia ambas cosas:

Requests HTTP
→
Scheduler (continuous batching)
→
Prefill por chunks + decode
→
KV cache en bloques (PagedAttention)
→
Tokens en streaming
TécnicaQué resuelveEstado en vLLM V1
PagedAttentionEl KV cache se guarda en bloques pequeños de tamaño fijo, como páginas de memoria virtual: casi sin fragmentación ni reservas desperdiciadasSiempre activo
Continuous batchingEn cada paso entran requests nuevos y salen los terminados; la GPU no espera al request más largoSiempre activo
Chunked prefillLos prompts largos se parten en trozos que se mezclan con pasos de decode, así un prompt de 30k tokens no congela al restoActivo por defecto
Automatic Prefix CachingReutiliza el KV cache de prefijos idénticos (system prompt, few-shot, historial de chat)Activo por defecto
Qué cambió: desde vLLM V1 el motor antiguo (V0) ya no existe y la forma oficial de levantar el servidor es la CLI vllm serve. Si ves tutoriales con python -m vllm.entrypoints.openai.api_server o con --enable-chunked-prefill, son anteriores: esos flags ya son el comportamiento por defecto.

2. Hardware y modelo de ejemplo

vLLM necesita una GPU NVIDIA con compute capability 7.5 o superior (T4, serie RTX 20xx en adelante, L4, A10G, A100, H100, B200). La V100 (7.0) ya no está soportada. La guía usa Qwen/Qwen3-4B-Instruct-2507: un modelo instruct sin modo de razonamiento, multilingüe, con buen español y portugués, que cabe holgado en 24 GB.

EscenarioGPUModeloNotas
Recomendado1× L4 / A10G (24 GB)Qwen/Qwen3-4B-Instruct-2507 en BF16~8 GB de pesos; el resto queda para KV cache con --max-model-len 8192
Presupuesto reducido1× T4 (16 GB, p. ej. Colab o una VM spot)Qwen/Qwen2.5-1.5B-InstructLa T4 no tiene BF16: corre en FP16 (--dtype half)
Más calidad en español1× A100/H100 (40-80 GB)Qwen/Qwen3-8B o BSC-LT/salamandra-7b-instructQwen3-8B razona por defecto; los reasoning parsers se ven en la guía avanzada

Tiempos esperables: instalación ~5 min, descarga del modelo 2-5 min, y el primer arranque tarda 1-3 min extra porque vLLM compila el modelo con torch.compile y captura CUDA graphs (queda en caché para los arranques siguientes). Todo lo de esta guía se recorre en menos de una hora.

¿Cuánto KV cache necesito?

El cálculo es simple y conviene hacerlo antes de elegir --max-model-len. Por token se guardan K y V en cada capa: 2 × capas × kv_heads × head_dim × bytes.

python — kv_budget.py
import json

from huggingface_hub import hf_hub_download

MODEL = "Qwen/Qwen3-4B-Instruct-2507"
VRAM_GB = 24          # L4 / A10G
GPU_UTIL = 0.90       # --gpu-memory-utilization
PARAMS_B = 4.0        # miles de millones de parámetros
OVERHEAD_GB = 1.5     # activaciones, CUDA graphs, buffers (aprox.)
MAX_MODEL_LEN = 8192

with open(hf_hub_download(MODEL, "config.json")) as f:
    cfg = json.load(f)
head_dim = cfg.get("head_dim") or cfg["hidden_size"] // cfg["num_attention_heads"]
bytes_per_token = 2 * cfg["num_hidden_layers"] * cfg["num_key_value_heads"] * head_dim * 2  # BF16

weights_gb = PARAMS_B * 2
kv_gb = VRAM_GB * GPU_UTIL - weights_gb - OVERHEAD_GB
kv_tokens = int(kv_gb * 1024**3 / bytes_per_token)

print(f"KV por token: {bytes_per_token / 1024:.0f} KiB")
print(f"KV disponible: {kv_gb:.1f} GB ≈ {kv_tokens:,} tokens")
print(f"Conversaciones simultáneas a {MAX_MODEL_LEN} tokens: ~{kv_tokens // MAX_MODEL_LEN}")

Para Qwen3-4B (36 capas, 8 KV heads, head_dim 128) salen ~144 KiB por token: unos 80 mil tokens de KV cache en una L4, o ~10 conversaciones llenas de 8k a la vez. Al arrancar, vLLM imprime su propia cuenta (GPU KV cache size y Maximum concurrency); compárala con la tuya.

Ángulo es/pt: los tokenizers multilingües suelen gastar más tokens por palabra en español y portugués que en inglés. Un mismo documento ocupa más KV cache y más pasos de decode, así que dimensiona con prompts reales en tu idioma (sección 8), no con estimaciones hechas en inglés.

3. Instalación

vLLM trae sus propios kernels CUDA compilados contra una versión fija de PyTorch, así que la documentación pide un entorno nuevo. Con uv y --torch-backend=auto se elige automáticamente el índice de PyTorch que corresponde a tu driver (los binarios por defecto son CUDA 12.9, con variantes 12.8 y 13.0). Python soportado según la doc: 3.11 a 3.14.

bash — entorno limpio
# 1) Comprobar driver y GPU (compute capability >= 7.5)
nvidia-smi --query-gpu=name,compute_cap,memory.total --format=csv

# 2) Entorno nuevo con uv
curl -LsSf https://astral.sh/uv/install.sh | sh
uv venv --python 3.12 --seed
source .venv/bin/activate

# 3) vLLM + PyTorch adecuado para el driver
uv pip install vllm --torch-backend=auto

# 4) Cliente OpenAI y datasets (para las secciones 5 y 8)
uv pip install openai datasets

# 5) Verificar
python -c "import vllm, torch; print(vllm.__version__, torch.__version__, torch.cuda.is_available())"
vllm --help
No mezcles entornos: instalar vLLM encima de un entorno de entrenamiento (con otra versión de PyTorch, flash-attn o transformers) es la causa más común de errores raros de símbolos CUDA. Mantén un venv o contenedor solo para serving. En un cluster, la imagen oficial vllm/vllm-openai evita el problema.

Seguridad: --api-key (o VLLM_API_KEY) solo protege las rutas bajo /v1, /v2, /inference y /cohere. Otras rutas, como /invocations, exponen la misma inferencia sin autenticación. Para exponer el servidor fuera de tu máquina pon un reverse proxy (nginx, Caddy, un API gateway) delante y no abras el puerto 8000 directamente.

5. Hablarle con el cliente OpenAI

El servidor implementa /v1/chat/completions, /v1/completions y /v1/models, así que cualquier SDK o herramienta compatible con OpenAI funciona cambiando la base_url. El chat template del modelo se aplica en el servidor: tú solo mandas messages.

Con curl
bash
curl -s http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "latam-chat",
    "messages": [
      {"role": "system", "content": "Eres un asistente técnico. Responde en español neutro y en no más de 5 líneas."},
      {"role": "user", "content": "¿Qué diferencia hay entre prefill y decode?"}
    ],
    "max_tokens": 300
  }' | python -m json.tool
Con Python: respuesta completa y streaming
python — cliente.py
import os
import time

from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8000/v1",
    # Si el servidor corre sin --api-key, cualquier string sirve
    api_key=os.environ.get("VLLM_API_KEY", "EMPTY"),
)
MODEL = "latam-chat"

# 1) Respuesta completa, en español
resp = client.chat.completions.create(
    model=MODEL,
    messages=[
        {"role": "system", "content": "Eres un asistente para equipos de ingeniería en Latinoamérica. Responde en español."},
        {"role": "user", "content": "Explica en tres viñetas qué es el KV cache."},
    ],
    max_tokens=300,
    temperature=0.7,
    # Parámetros que no son de OpenAI van en extra_body
    extra_body={"top_k": 20, "repetition_penalty": 1.05},
)
print(resp.choices[0].message.content)
print("uso:", resp.usage)

# 2) Streaming, en portugués, midiendo el time-to-first-token
t0 = time.perf_counter()
ttft = None
stream = client.chat.completions.create(
    model=MODEL,
    messages=[
        {"role": "system", "content": "Você é um assistente técnico. Responda em português do Brasil."},
        {"role": "user", "content": "O que é continuous batching? Responda em um parágrafo."},
    ],
    max_tokens=300,
    stream=True,
    stream_options={"include_usage": True},
)
for chunk in stream:
    # El último chunk solo trae usage y no tiene choices
    if chunk.choices and chunk.choices[0].delta.content:
        if ttft is None:
            ttft = time.perf_counter() - t0
        print(chunk.choices[0].delta.content, end="", flush=True)
    if chunk.usage and ttft is not None:
        total = time.perf_counter() - t0
        print(f"\n\nTTFT={ttft:.2f}s | {chunk.usage.completion_tokens} tokens en {total:.2f}s")
Prompts es/pt: fija el idioma y la variante en el system prompt ("español neutro", "español de Chile", "português do Brasil"). Los modelos multilingües tienden a cambiar a inglés o a mezclar español y portugués cuando el usuario escribe poco texto; probar ambos idiomas desde el primer día evita sorpresas.

Para un modelo base (sin chat template) usa client.completions.create(model=..., prompt=...) sobre /v1/completions; con modelos instruct usa siempre chat.

6. Inferencia offline en batch con LLM

Cuando no necesitas un servidor (generar datos sintéticos, evaluar un checkpoint, traducir un corpus) la clase LLM carga el modelo en el mismo proceso y procesa miles de prompts con el mismo scheduler. Es la forma más rápida de pasar un dataset entero por el modelo.

python — batch_offline.py
import json

from vllm import LLM

llm = LLM(
    model="Qwen/Qwen3-4B-Instruct-2507",
    max_model_len=8192,
    gpu_memory_utilization=0.90,
    # dtype="half",  # descomentar en T4
)

# Por defecto vLLM toma temperature/top_p/top_k del generation_config.json del modelo
params = llm.get_default_sampling_params()
params.max_tokens = 400
print("sampling por defecto:", params)

preguntas = [
    ("es", "¿Por qué en el español rioplatense se usa 'vos' en lugar de 'tú'?"),
    ("es", "Resume en dos frases qué es la fotosíntesis."),
    ("pt", "Explique o que é a Lei Geral de Proteção de Dados (LGPD)."),
    ("pt", "Dê três dicas para economizar energia em casa."),
]
system = {
    "es": "Responde en español, de forma clara y breve.",
    "pt": "Responda em português do Brasil, de forma clara e breve.",
}

# Una conversación por pregunta; llm.chat aplica el chat template del modelo
conversaciones = [
    [{"role": "system", "content": system[lang]}, {"role": "user", "content": q}]
    for lang, q in preguntas
]
outputs = llm.chat(conversaciones, params)

with open("respuestas_es_pt.jsonl", "w", encoding="utf-8") as f:
    for (lang, q), out in zip(preguntas, outputs):
        texto = out.outputs[0].text
        f.write(json.dumps({"lang": lang, "pregunta": q, "respuesta": texto}, ensure_ascii=False) + "\n")
        print(f"[{lang}] {q}\n{texto}\n")

Para texto plano (modelo base, completar frases, scoring) usa generate con SamplingParams explícitos:

python — generate_base.py
from vllm import LLM, SamplingParams

llm = LLM(model="Qwen/Qwen3-4B-Instruct-2507", max_model_len=4096)

prompts = [
    "La cordillera de los Andes atraviesa",
    "O Rio Amazonas é importante porque",
]
# n=2: dos muestras por prompt; seed fija para reproducibilidad
params = SamplingParams(temperature=0.8, top_p=0.95, max_tokens=80, n=2, seed=1234)

for out in llm.generate(prompts, params):
    print("PROMPT:", out.prompt)
    for i, c in enumerate(out.outputs):
        print(f"  [{i}] {c.text.strip()}")
Una cosa a la vez: LLM(...) también reserva el 90% de la VRAM. No lo corras en la misma GPU donde ya está vllm serve: detén el servidor o usa otra GPU (CUDA_VISIBLE_DEVICES=1 python batch_offline.py).

# GPU: uso, memoria y potencia cada 2 s

Este script, sin dependencias, toma dos muestras de /metrics y calcula throughput de generación, TTFT medio y acierto del prefix cache en ese intervalo:

python — watch_metrics.py
import time
import urllib.request

URL = "http://127.0.0.1:8000/metrics"
WINDOW_S = 10


def scrape() -> dict[str, float]:
    """Suma cada métrica sobre todas sus etiquetas (un solo modelo servido)."""
    text = urllib.request.urlopen(URL, timeout=5).read().decode()
    values: dict[str, float] = {}
    for line in text.splitlines():
        if line.startswith("#") or not line.strip():
            continue
        name_labels, _, value = line.rpartition(" ")
        name = name_labels.split("{", 1)[0]
        values[name] = values.get(name, 0.0) + float(value)
    return values


def delta(a: dict, b: dict, key: str) -> float:
    return b.get(key, 0.0) - a.get(key, 0.0)


a = scrape()
time.sleep(WINDOW_S)
b = scrape()

gen_tps = delta(a, b, "vllm:generation_tokens_total") / WINDOW_S
n_ttft = delta(a, b, "vllm:time_to_first_token_seconds_count")
ttft = delta(a, b, "vllm:time_to_first_token_seconds_sum") / n_ttft if n_ttft else float("nan")
q = delta(a, b, "vllm:prefix_cache_queries_total")
hit = delta(a, b, "vllm:prefix_cache_hits_total") / q if q else float("nan")

print(f"running={b.get('vllm:num_requests_running', 0):.0f} "
      f"waiting={b.get('vllm:num_requests_waiting', 0):.0f} "
      f"kv={100 * b.get('vllm:kv_cache_usage_perc', 0):.1f}%")
print(f"generación={gen_tps:.0f} tok/s | TTFT medio={ttft:.3f}s | prefix hit={hit:.1%}")

Córrelo mientras el benchmark de la sección siguiente está en marcha. Con un system prompt largo y fijo (por ejemplo, instrucciones de estilo en español compartidas por todos los usuarios) deberías ver un acierto de prefix cache alto y un TTFT menor.

8. Un primer benchmark con vllm bench serve

Medir con ab o con un script que promedia tokens/s por request no dice nada útil: no mide TTFT ni latencia entre tokens y confunde velocidad por usuario con throughput agregado. vllm bench serve lanza carga contra el servidor ya levantado y reporta las métricas que importan.

Paso 1: carga sintética
bash — prompts aleatorios 1024 → 256 tokens
# --model se usa para el tokenizer; --served-model-name debe coincidir con el servidor
vllm bench serve \
  --backend vllm \
  --model Qwen/Qwen3-4B-Instruct-2507 \
  --served-model-name latam-chat \
  --host 127.0.0.1 --port 8000 \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 256 \
  --num-prompts 200 \
  --max-concurrency 16 \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,90,99 \
  --save-result --result-dir ./bench
Métrica del reporteQué significaPara qué sirve
Request throughput (req/s)Requests completados por segundoCapacidad del servidor
Output token throughput (tok/s)Tokens generados por segundo, sumando todos los usuariosCosto por token y comparación entre GPUs
TTFT (p50/p90/p99)Tiempo hasta el primer tokenSensación de "responde rápido"; sube con prompts largos y con la cola
TPOT / ITLTiempo por token de salida / entre tokensVelocidad de lectura del streaming; sube con la concurrencia
E2ELLatencia total del requestTimeouts de clientes y SLOs

Repite con --max-concurrency 1, 4, 16 y 64: verás que el throughput total sube mientras el ITL por usuario empeora. El punto donde el p90 de ITL o de TTFT supera lo aceptable para tu producto es tu capacidad real por GPU.

Paso 2: prompts reales en español y portugués

Los prompts aleatorios no reflejan tu tráfico. Este script toma preguntas reales en español y portugués de CohereLabs/aya_dataset, las escribe en el formato custom de vLLM (un JSONL con campo prompt) y mide cuántos tokens por palabra usa el tokenizer en cada idioma:

python — make_prompts_es_pt.py
import json
import random

from datasets import load_dataset
from transformers import AutoTokenizer

MODEL = "Qwen/Qwen3-4B-Instruct-2507"
N_PER_LANG = 250

tok = AutoTokenizer.from_pretrained(MODEL)
ds = load_dataset("CohereLabs/aya_dataset", split="train")
ds = ds.filter(lambda ex: ex["language_code"] in {"spa", "por"})

random.seed(0)
rows = []
for code in ("spa", "por"):
    sub = ds.filter(lambda ex, c=code: ex["language_code"] == c)
    idx = random.sample(range(len(sub)), k=min(N_PER_LANG, len(sub)))
    n_tok = n_words = 0
    for i in idx:
        text = sub[i]["inputs"].strip()
        n_tok += len(tok(text)["input_ids"])
        n_words += len(text.split())
        rows.append({"prompt": text})
    print(f"{code}: {len(idx)} prompts | {n_tok / len(idx):.0f} tokens/prompt | "
          f"{n_tok / max(n_words, 1):.2f} tokens/palabra")

random.shuffle(rows)
with open("prompts_es_pt.jsonl", "w", encoding="utf-8") as f:
    for r in rows:
        f.write(json.dumps(r, ensure_ascii=False) + "\n")
print("escrito prompts_es_pt.jsonl con", len(rows), "prompts")
bash — benchmark con el dataset es/pt
# Sin --skip-chat-template, el cliente aplica el chat template del modelo a cada prompt
vllm bench serve \
  --backend vllm \
  --model Qwen/Qwen3-4B-Instruct-2507 \
  --served-model-name latam-chat \
  --host 127.0.0.1 --port 8000 \
  --endpoint /v1/completions \
  --dataset-name custom \
  --dataset-path prompts_es_pt.jsonl \
  --custom-output-len 256 \
  --num-prompts 500 \
  --max-concurrency 16 \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,90,99 \
  --save-result --result-dir ./bench
Ojo con el prefix cache: si repites la misma corrida contra el mismo servidor, los prompts ya están en caché y el TTFT sale artificialmente bajo. Reinicia el servidor entre corridas que quieras comparar. Cambiar --seed (por defecto 0) solo ayuda si el archivo tiene más prompts que --num-prompts: con los 500 prompts completos, una semilla distinta solo los reordena y siguen en caché.
Cómo leerlo: compara los tokens/palabra de español y portugués con los de un texto en inglés de largo similar. Si tu tokenizer gasta bastante más en es/pt, la misma conversación cuesta más KV cache, más TTFT y más dinero por respuesta. Es un argumento concreto para entrenar o extender el tokenizer (ver la guía de tokenizer training).
