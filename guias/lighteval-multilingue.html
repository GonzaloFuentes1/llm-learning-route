Evaluación multilingüe con lighteval: tareas es/pt, formulaciones CF/MCF y PoETa v2

Cómo medir modelos base e instruct en español y portugués con lighteval: tareas nativas (ENEM, OAB, OpenBookQA-es, Global-MMLU, Belebele), formulaciones cloze vs opción múltiple, tareas propias como LatamQA y CHOCLO, intervalos de confianza desde los details y PoETa v2 como suite de referencia para portugués.

1. lighteval, lm-eval y PoETa v2: cuándo usar cada uno

Checkpoint (HF o local)
→
lighteval + vLLM
→
Tareas es/pt nativas + custom
→
results JSON + details parquet
→
IC y comparación pareada

La guía de evaluación con lm-eval-harness cubre el harness más usado para modelos base. lighteval (Hugging Face) aporta algo distinto: un sistema de plantillas multilingües que evalúa la misma tarea en tres formulaciones (cloze, opción múltiple con letras e híbrida) y con varias normalizaciones de log-probabilidad. Es el harness que HF usó para seleccionar tareas multilingües en FineWeb2 (FineTasks) y el que conviene para medir checkpoints tempranos de pretraining, donde la formulación importa mucho.

No mezcles números entre harnesses. ENEM en lighteval (log-likelihood, exámenes 2022-2024) y ENEM en PoETa v2 (generación greedy, exámenes 2009-2017) no son el mismo experimento: cambian el prompt, la formulación, la normalización y hasta los años. Compara modelos siempre dentro del mismo harness, versión y configuración.

2. Instalación en un entorno aislado

La última release en PyPI es lighteval 0.13.0 (nov-2025), cuyo extra [vllm] fija vllm>=0.10.0,<0.10.2. La rama main (0.13.1.dev0, activa en octubre de 2026) pide vllm>=0.11 y es la opción para arquitecturas recientes. 4. Primera corrida: tareas nativas es/pt con vLLM

Para un modelo base evaluado por log-likelihood, desactiva el chat template con override_chat_template=false: lighteval lo aplica automáticamente si el tokenizer trae uno, y muchos repos base lo incluyen.

bash
MODEL=HuggingFaceTB/SmolLM3-3B-Base

lighteval vllm \
  "model_name=$MODEL,dtype=bfloat16,max_model_length=4096,gpu_memory_utilization=0.85,override_chat_template=false" \
  "enem_por_cf:2024|0,enem_por_mcf:2024|0,oab_exams_por_cf|0,openbookqa_spa_cf|0,openbookqa_spa_mcf|5,global_mmlu_all_spa_mcf:high_school_biology|5,global_mmlu_all_por_mcf:high_school_biology|5,belebele_spa_Latn_cf|0,belebele_por_Latn_cf|0" \
  --load-tasks-multilingual \
  --save-details \
  --output-dir results

# Resultados: results/results/<modelo>/results_<timestamp>.json
# Details:    results/details/<modelo>/<timestamp>/details_<tarea>_<timestamp>.parquet

El JSON trae, por tarea ("enem_por_cf:2024|0"), cada métrica y su _stderr. Las métricas se llaman según la normalización: acc (sin normalizar, la que usa MCF con letras), acc_norm_token (log-prob dividida por número de tokens), acc_norm (por número de caracteres) y acc_norm_pmi (PMI contra la respuesta sin pregunta).

5. Formulaciones CF, MCF e Hybrid y normalizaciones

La misma pregunta se puede presentar de tres formas. En español la plantilla usa los literales Pregunta / Respuesta, y en portugués sus equivalentes; con lighteval tasks inspect ves el texto exacto.

text
CF (cloze): se puntúa el texto completo de cada opción
  Pregunta: ¿Qué sitio arqueológico peruano es el ícono de la arquitectura incaica?
  Respuesta: | Machu Picchu | Sacsayhuamán | Caral | Coricancha

MCF (opción múltiple): opciones en el prompt, se puntúa la letra
  Pregunta: ...  A. Machu Picchu  B. Sacsayhuamán  C. Caral  D. Coricancha
  Respuesta: | A | B | C | D

Hybrid: opciones en el prompt, pero se puntúa el texto completo
  Respuesta: | Machu Picchu | Sacsayhuamán | Caral | Coricancha
NormalizaciónMétricaQué corrigeCuándo
Ningunaacc-MCF (todas las opciones son una letra)
LogProbTokenNormacc_norm_tokenOpciones largas penalizadasCF en idiomas no ingleses (la que usa FineWeb2; FineTasks sugiere quedarse con la mejor entre token y caracteres según el idioma)
LogProbCharNormacc_normIgual, pero independiente del tokenizerComparar modelos con tokenizers distintos
LogProbPMINormacc_norm_pmiOpciones a priori improbablesTareas difíciles o con términos raros (FineWeb2 la usa en AGIEval y MMLU traducido)

La regla práctica, documentada por OLMES y por FineTasks: los modelos chicos o los checkpoints tempranos rinden al azar en MCF porque todavía no aprendieron el formato "elige la letra", mientras CF ya muestra una señal monótona. Por eso OLMES evalúa ambas formulaciones y reporta la mejor. Compruébalo con tres checkpoints públicos de OLMo-2 1B:

bash
cat > tasks_es_pt.txt <<'EOF'
# una tarea por línea (las líneas con # se ignoran)

belebele_spa_Latn_cf|0
belebele_por_Latn_cf|0

EOF

for REV in stage1-step10000-tokens21B stage1-step100000-tokens210B stage1-step1000000-tokens2098B; do
  lighteval vllm \
    "model_name=allenai/OLMo-2-0425-1B,revision=$REV,dtype=bfloat16,max_model_length=4096,override_chat_template=false" \

En el cluster: convierte el loop en un array de SLURM (#SBATCH --array=0-2, REV=${CKPTS[$SLURM_ARRAY_TASK_ID]}), un checkpoint por job y con su propio --output-dir, para que un fallo no tumbe al resto. Agrega --wandb (con WANDB_PROJECT exportado) para ver las curvas en vivo. Para checkpoints propios usa model_name=/ruta/checkpoints/step-N sin revision. La plantilla de job está en la guía de cluster.
python
import glob
import json
import os

import pandas as pd

REVS = ["stage1-step10000-tokens21B", "stage1-step100000-tokens210B", "stage1-step1000000-tokens2098B"]

rows = []
for rev in REVS:
    files = glob.glob(f"results/olmo-{rev}/results/**/results_*.json", recursive=True)
    with open(max(files, key=os.path.getmtime), encoding="utf-8") as f:
        results = json.load(f)["results"]
    for task, metrics in results.items():
        if task == "all":
            continue
        base, _, form = task.split("|")[0].rpartition("_")   # p.ej. openbookqa_spa / cf
        for metric, value in metrics.items():
            if not metric.endswith("_stderr"):
                rows.append({"tarea": base, "formulación": form, "métrica": metric,
                             "tokens": rev.split("-")[-1], "score": value})

df = pd.DataFrame(rows)
table = df.pivot_table(index=["tarea", "formulación", "métrica"], columns="tokens", values="score")
print(table[[r.split("-")[-1] for r in REVS]].round(3).to_string())
Cómo leerlo: una tarea útil para decidir ablaciones de pretraining debe subir de forma monótona con los tokens, quedar claramente sobre el azar (25% con 4 opciones) y tener poco ruido entre checkpoints vecinos. Si MCF se queda plano en ~25% mientras CF sube, usa CF para tus modelos pequeños. Para la parte estadística (IC y tests pareados) sigue en la guía de evaluación estadísticamente rigurosa.

6. Tarea custom: LatamQA en tres formulaciones (y su versión en inglés)

LatamQA (Inria Chile) tiene 18,907 preguntas de opción múltiple sobre cultura latinoamericana en inria-chile/latamqa_mcq_es-la (público). Cada fila trae question, answer, distractor1-3, el article_id de Wikipedia de origen y la traducción al inglés de todo (question_en, answer_en...). Con eso puedes medir, con las mismas preguntas, la brecha español-inglés de tu modelo. Las variantes latamqa_mcq_es-es y latamqa_mcq_pt-br existen pero son gated (acceso manual).

El archivo define un TASKS_TABLE que lighteval carga con --custom-tasks. Dos detalles importan: las opciones se barajan con una semilla derivada de la pregunta (la respuesta correcta no puede quedar siempre en la A), y cada Doc guarda article_id en specific para calcular después errores estándar por cluster.

python — latamqa_task.py
"""LatamQA (es-LA) como tarea custom de lighteval: CF, MCF e Hybrid, en español e inglés."""
import random
import zlib

from lighteval.metrics.dynamic_metrics import LogLikelihoodAccMetric
from lighteval.metrics.normalizations import LogProbCharNorm, LogProbPMINorm, LogProbTokenNorm
from lighteval.tasks.lighteval_task import LightevalTaskConfig
from lighteval.tasks.multilingual.utils.task_utils import get_metrics_for_formulation
from lighteval.tasks.templates.multichoice import get_mcq_prompt_function
from lighteval.tasks.templates.utils.formulation import (
    CFFormulation,
    HybridFormulation,
    MCFFormulation,
)
from lighteval.utils.language import Language

def question_key(line: dict) -> int:
    # Semilla estable entre procesos (hash() de Python cambia en cada ejecución)
    return zlib.crc32(line["question"].encode("utf-8"))

def make_adapter(suffix: str):
    """suffix='' usa los campos en español; suffix='_en' la traducción al inglés."""
    def adapter(line: dict) -> dict:
        options = [line[f"answer{suffix}"]] + [line[f"distractor{i}{suffix}"] for i in (1, 2, 3)]
        order = list(range(4))
        random.Random(question_key(line)).shuffle(order)   # mismo orden en es y en
        return {
            "question": line[f"question{suffix}"],
            "choices": [options[i] for i in order],
            "gold_idx": order.index(0),
        }
    return adapter

def with_metadata(prompt_fn):
    """Guarda article_id y un id de pregunta en Doc.specific (queda en los details)."""
    def fn(line: dict, task_name: str):
        doc = prompt_fn(line, task_name)
        if doc is not None:
            doc.specific = {"article_id": int(line["article_id"]), "qid": question_key(line)}
        return doc
    return fn

TASKS_TABLE = [
    LightevalTaskConfig(
        name=f"latamqa_{language.value}_{formulation.name.lower()}",
        prompt_function=with_metadata(
            get_mcq_prompt_function(language, make_adapter(suffix), formulation=formulation)
        ),
        hf_repo="inria-chile/latamqa_mcq_es-la",
        hf_subset="default",
        hf_avail_splits=["train"],
        evaluation_splits=("train",),
        hf_filter=lambda line: all(line[k] for k in line if k not in ("article_id", "title")),
        metrics=get_metrics_for_formulation(
            formulation,
            [
                LogLikelihoodAccMetric(normalization=LogProbTokenNorm()),
                LogLikelihoodAccMetric(normalization=LogProbCharNorm()),
                LogLikelihoodAccMetric(normalization=LogProbPMINorm()),
            ],
        ),
    )
    for language, suffix in [(Language.SPANISH, ""), (Language.ENGLISH, "_en")]
    for formulation in [MCFFormulation(), CFFormulation(), HybridFormulation()]
]
bash

lighteval vllm \

Variedad y contaminación: LatamQA se generó a partir de artículos de Wikipedia, que casi seguro están en tu corpus de pretraining. Mide conocimiento cultural, no generalización. Reporta el número junto a una tarea con test privado y nunca la uses para elegir mezclas de datos que incluyan Wikipedia en español sin decirlo.

7. Tarea generativa de respuesta corta: CHOCLO

CHOCLO (latam-gpt/CHOCLO) tiene 104,847 pares pregunta-respuesta sobre entidades de 18 países latinoamericanos, con país, categoría y dificultad. Muchas respuestas de referencia son frases descriptivas y no solo la entidad, así que el exact match casi nunca acierta. Usa F1 de tokens multilingüe como señal barata y guarda los details para puntuar después con un juez. La columna Country mezcla mayúsculas ("chile", "México", "méxico"): normalízala en el filtro.

python — choclo_task.py
"""CHOCLO como tarea generativa de lighteval, una subtarea por país."""
from functools import partial

from lighteval.metrics.dynamic_metrics import (
    MultilingualQuasiExactMatchMetric,
    MultilingualQuasiF1ScoreMetric,
)
from lighteval.tasks.lighteval_task import LightevalTaskConfig
from lighteval.tasks.templates.qa import get_qa_prompt_function
from lighteval.utils.language import Language

COUNTRIES = {"chile": "chile", "mexico": "méxico", "peru": "perú",
             "argentina": "argentina", "colombia": "colombia"}

def same_country(target: str, line: dict) -> bool:
    return (line["Country"] or "").strip().lower() == target and bool(line["Answer"])

TASKS_TABLE = [
    LightevalTaskConfig(
        name=f"choclo_{slug}",
        prompt_function=get_qa_prompt_function(
            Language.SPANISH,
            lambda line: {"question": line["Question"], "choices": [line["Answer"]]},
        ),
        hf_repo="latam-gpt/CHOCLO",
        hf_subset="default",
        hf_avail_splits=["train"],
        evaluation_splits=("train",),
        hf_filter=partial(same_country, country),
        generation_size=64,
        stop_sequence=("\n",),
        metrics=[
            MultilingualQuasiF1ScoreMetric(Language.SPANISH),
            MultilingualQuasiExactMatchMetric(Language.SPANISH, "prefix"),
        ],
    )
    for slug, country in COUNTRIES.items()
]

Se corre igual que LatamQA: --custom-tasks choclo_task.py "choclo_chile|3,choclo_mexico|3,choclo_peru|3" --max-samples 500 --save-details. Los few-shot salen del mismo split filtrado.

F1 no es el score final. Con respuestas abiertas, F1 de tokens castiga paráfrasis correctas y premia respuestas que copian palabras de la pregunta. La auditoría independiente LatamBench reporta que, con corrección de Holm sobre todos los pares, el ranking completo de CHOCLO queda en un único grupo de empate estadístico, y que su juez todavía no está validado para CHOCLO (solo para Trueque). Usa los details (columna model_response) como entrada de la guía LLM-as-a-judge calibrado.

8. Modelos instruct y de razonamiento

Con un modelo instruct, lighteval detecta el chat template y lo aplica. En ese modo descarta las stop_sequence de la tarea (el modelo termina con su token de fin de turno). Además, si defines max_new_tokens en generation_parameters, reemplaza al generation_size de la tarea (con o sin chat template): clave para tareas como mgsm_spa, que trae generation_size=25. --remove-reasoning-tags está activo por defecto y elimina el bloque <think>...</think> antes de calcular la métrica. Para LatamGPT 70B (latam-gpt/Llama-3.1-70B-LatamGPT-SFT-1.0) agrega tensor_parallel_size=4 en 4 GPUs de 80 GB. Para modelos cerrados vía API existe lighteval eval (backend Inspect AI), que sirve para tareas generativas pero no da log-likelihoods.

bash
lighteval vllm \
  "model_name=Qwen/Qwen3-8B,dtype=bfloat16,max_model_length=16384,gpu_memory_utilization=0.9,generation_parameters={temperature:0.6,top_p:0.95,max_new_tokens:8192}" \
  "mgsm_spa|0,belebele_spa_Latn_mcf|0,flores200:eng_Latn-spa_Latn|0" \
  --load-tasks-multilingual \
  --reasoning-tags "[('<think>', '</think>')]" \
  --max-samples 250 \
  --save-details \
  --output-dir results
Exact match y razonamiento: mgsm_spa compara la respuesta completa con el número de referencia. Un modelo instruct que contesta "La respuesta es 18." pierde el punto aunque acierte. Revisa los details antes de concluir que el modelo no sabe matemática en español. Para razonamiento matemático serio usa métricas extractivas o un juez, y fija temperatura y semilla (o promedia varias semillas), como recomienda la literatura de reproducibilidad en reasoning.

9. De los details a intervalos de confianza y comparaciones pareadas

El _stderr del JSON supone preguntas independientes. En LatamQA varias preguntas salen del mismo artículo, así que el error real es mayor: hay que agrupar por article_id (errores estándar clustered, como propone Miller, 2024). Cada parquet de details tiene una fila por ítem con las columnas doc, metric y model_response.

python
import glob

import numpy as np
from datasets import load_dataset

MODEL = "HuggingFaceTB/SmolLM3-3B-Base"
METRIC = "acc_norm"   # normalización por caracteres

def load_details(task: str):
    # Los nombres de archivo llevan "|": corre esto en Linux/macOS (Windows no los admite)
    paths = sorted(glob.glob(f"results/details/{MODEL}/*/details_{task}_*.parquet"))
    det = load_dataset("parquet", data_files=paths[-1], split="train")
    y = np.array([m[METRIC] for m in det["metric"]], dtype=float)
    meta = [d["specific"] for d in det["doc"]]
    return y, np.array([m["article_id"] for m in meta]), np.array([m["qid"] for m in meta])

def clustered_ci(y: np.ndarray, clusters: np.ndarray, z: float = 1.96):
    n, mean = len(y), y.mean()
    naive_se = y.std(ddof=1) / np.sqrt(n)
    _, inv = np.unique(clusters, return_inverse=True)
    resid_by_cluster = np.bincount(inv, weights=y - mean)
    clustered_se = np.sqrt((resid_by_cluster ** 2).sum()) / n
    return mean, naive_se, clustered_se, (mean - z * clustered_se, mean + z * clustered_se)

y_es, art_es, qid_es = load_details("latamqa_spa_cf|0")
y_en, art_en, qid_en = load_details("latamqa_eng_cf|0")

for name, y, art in [("es", y_es, art_es), ("en", y_en, art_en)]:
    mean, se, cse, (lo, hi) = clustered_ci(y, art)
    print(f"LatamQA-{name}: {mean:.3f}  SE ingenuo={se:.4f}  SE clustered={cse:.4f}  IC95=[{lo:.3f}, {hi:.3f}]")

# Brecha es - en pareada por pregunta (mismas preguntas, mismo orden de opciones)
en_by_qid = dict(zip(qid_en, y_en))
pairs = [(a, y, en_by_qid[q]) for a, y, q in zip(art_es, y_es, qid_es) if q in en_by_qid]
art_p = np.array([p[0] for p in pairs])
diff = np.array([p[1] - p[2] for p in pairs])
gap, _, cse, (lo, hi) = clustered_ci(diff, art_p)
print(f"Brecha es-en: {gap:+.3f}  IC95=[{lo:+.3f}, {hi:+.3f}]  (n={len(diff)})")
Por qué pareado: la varianza de la diferencia pareada es mucho menor que la de comparar dos promedios independientes, porque la dificultad de cada pregunta se cancela. Con el mismo razonamiento comparas dos checkpoints sobre los mismos ítems. El cruce por qid descarta los ítems que no aparecen en ambas corridas. Tests pareados, bootstrap y análisis de potencia, en evaluación estadísticamente rigurosa.

10. PoETa v2: la suite de referencia para portugués

PoETa v2 (Almeida et al., 2025) es la evaluación más extensa de LLMs en portugués: más de 40 tareas (44 en configs/poeta_v2_full.json: 12 nativas y 32 traducidas, unos 12K ejemplos) y más de 20 modelos evaluados. El paper estudia cómo la inversión de cómputo y la adaptación al idioma afectan el rendimiento, y la brecha con tareas equivalentes en inglés. Las tareas nativas incluyen ASSIN 2 (RTE y STS), BLUEX, ENEM, FaQuAD, TweetSentBR, BRoverbs (refranes brasileños) y otras como inferbr, repro y mina_br. Las traducidas cubren ARC, BoolQ, GSM8K y MATH en formato de opción múltiple, BIG-bench, discurso de odio, entre otras.

El leaderboard del repositorio muestra el argumento que más le importa a LatamGPT: Sabiá (7B, 1T tokens de pretraining + 10B extra en portugués) obtiene 32.4 de NPM frente a 19.9 de Llama 1 7B (1T), y Curió 7B (2T + 100B en portugués) obtiene 34.8 frente a 29.5 de Llama 2 7B (2T). Es el mismo patrón que se busca con el continual pretraining en español.

NPM (Normalized Preferred Metric) normaliza cada tarea entre su baseline aleatorio y el máximo: NPM = 100 · (score − random) / (max − random), y promedia. Así una tarea binaria con 50% de azar no pesa igual que una de cinco opciones. Puedes aplicar la misma idea a tus resultados de lighteval para tener un agregado es/pt comparable entre checkpoints (no con el número oficial de PoETa):

python
import glob
import json
import os

MODEL = "HuggingFaceTB/SmolLM3-3B-Base"
METRIC = "acc_norm"

# Baseline aleatorio = 1 / número de opciones (igual que random_score en poeta_v2_full.json)
TASKS = {"enem_por_cf:2024|0": (1 / 5, "pt"), "oab_exams_por_cf|0": (1 / 4, "pt"),
         "belebele_por_Latn_cf|0": (1 / 4, "pt"), "openbookqa_spa_cf|0": (1 / 4, "es"),
         "belebele_spa_Latn_cf|0": (1 / 4, "es")}

files = glob.glob(f"results/results/{MODEL}/results_*.json")
with open(max(files, key=os.path.getmtime), encoding="utf-8") as f:
    results = json.load(f)["results"]

npm_by_lang = {"es": [], "pt": []}
for task, (rnd, lang) in TASKS.items():
    if task in results and METRIC in results[task]:
        npm_by_lang[lang].append(100 * (results[task][METRIC] - rnd) / (1.0 - rnd))

for lang, vals in npm_by_lang.items():
    if vals:
        print(f"NPM-{lang}: {sum(vals) / len(vals):.1f}  ({len(vals)} tareas)")

Modelos nuevos en PoETa: con transformers==4.41.1 el backend gpt no carga arquitecturas posteriores a mediados de 2024. Para esos modelos, PoETa trae un backend vllm que llama a un endpoint compatible con OpenAI (http://localhost:8000/v1 por defecto). Levántalo con vllm serve en otro entorno y en la config pon "model": "vllm" y el nombre del modelo servido en "model_for_inference". Es un backend de chat y solo de generación, así que tiene sentido para modelos instruct.
