Evaluación para español/portugués con lm-eval-harness

Cómo correr benchmarks multilingüe en la práctica: instalación de lm-evaluation-harness, ejecución de MGSM, Global-MMLU, FLORES-200 e IFEval, creación de tasks personalizados para español/portugués (LatamQA, Trueque) y detección de contaminación.

1. Instalación de lm-evaluation-harness

bash
git clone https://github.com/EleutherAI/lm-evaluation-harness
cd lm-evaluation-harness
pip install -e ".[vllm,ifeval]"   # vLLM (recomendado para velocidad) + dependencias de IFEval (langdetect, immutabledict, nltk)
# pip install -e ".[api]"         # si vas a evaluar via API (OpenAI-compatible)
# lm_eval ls tasks | grep _es     # verifica los nombres exactos de las tareas disponibles
Backend recomendado: usa --model vllm para modelos locales (3-5x más rápido que HuggingFace estándar). Requiere GPU con suficiente VRAM para el modelo. Para modelos instruct agrega --apply_chat_template (activa fewshot_as_multiturn automáticamente); para modelos base, omítelo.

2. Correr benchmarks estándar

Comando base

bash
# Benchmarks de conocimiento general
lm_eval \
  --model vllm \
  --model_args pretrained=models/mi-modelo-es,dtype=bfloat16,max_model_len=4096 \
  --tasks mmlu,arc_challenge,hellaswag \
  --num_fewshot 5 \
  --batch_size auto \
  --output_path resultados/run1/ \
  --log_samples

# IFEval (instruction following — siempre 0-shot)
lm_eval \
  --model vllm \
  --model_args pretrained=models/mi-modelo-es \
  --tasks ifeval \
  --num_fewshot 0 \
  --batch_size auto \
  --output_path resultados/run1/
Dónde quedan los resultados: con --output_path apuntando a un directorio, lm-eval escribe resultados/run1/<modelo_sanitizado>/results_<fecha>.json (y los samples_*.jsonl si usas --log_samples). Si le pasas un nombre terminado en .json, igual le agrega la fecha al nombre, así que no asumas una ruta fija: búscala con glob (sección 5).

Benchmarks multilingüe clave

bash
# MGSM — matemáticas en español (8-shot, chain-of-thought en español)
# variantes: mgsm_direct_es (sin CoT) y mgsm_en_cot_es (CoT en inglés)
lm_eval \
  --model vllm \
  --model_args pretrained=models/mi-modelo-es \
  --tasks mgsm_native_cot_es \
  --num_fewshot 8 \
  --output_path resultados/mgsm/

# Global-MMLU en español (set completo; global_mmlu_es es la versión Lite)
lm_eval \
  --model vllm \
  --model_args pretrained=models/mi-modelo-es \
  --tasks global_mmlu_full_es \
  --num_fewshot 5 \
  --output_path resultados/global_mmlu/

# FLORES-200 en→es y es→en (BLEU, TER y chrF). facebook/flores es gated:
# acepta los términos en HF y exporta HF_TOKEN. Para portugués: grupo flores_pt
lm_eval \
  --model vllm \
  --model_args pretrained=models/mi-modelo-es \
  --tasks spanish_bench_flores_en-es,spanish_bench_flores_es-en \
  --num_fewshot 5 \
  --output_path resultados/flores/
FLORES-200: es un benchmark de traducción, así que se mide con métricas de superposición (BLEU, chrF) y no con accuracy. Las tareas flores_* de lm-eval ya calculan chrF con sacrebleu; si generas las traducciones por fuera (p.ej. con vLLM), puntúalas con el script de abajo.
python — chrF++ con sacrebleu sobre FLORES+ (devtest)
# pip install sacrebleu datasets
# openlanguagedata/flores_plus es gated: acepta los términos en HF y exporta HF_TOKEN
from datasets import load_dataset
from sacrebleu.metrics import CHRF

refs = load_dataset("openlanguagedata/flores_plus", "spa_Latn", split="devtest")["text"]

# hipótesis: una traducción en→es por línea, en el mismo orden que el devtest
with open("resultados/flores_en-es.hyp.txt", encoding="utf-8") as f:
    hyps = [line.rstrip("\n") for line in f]
assert len(hyps) == len(refs), f"{len(hyps)} hipótesis vs {len(refs)} referencias"

chrfpp = CHRF(word_order=2)  # word_order=2 → chrF++
print(chrfpp.corpus_score(hyps, [refs]))

3. Suite de evaluación Latam (script SLURM)

Corre todos los benchmarks relevantes de un tirón en el cluster. Útil para comparar checkpoints.

bash — eval_latam.sh
#!/bin/bash
#SBATCH --job-name=eval-latam
#SBATCH --gres=gpu:1
#SBATCH --cpus-per-task=8
#SBATCH --mem=40G
#SBATCH --time=04:00:00
#SBATCH --output=logs/eval-%j.out

MODEL_PATH=$1   # pasar como argumento: sbatch eval_latam.sh models/checkpoint-1000
OUTPUT_DIR="resultados/$(basename $MODEL_PATH)"
mkdir -p $OUTPUT_DIR

TASKS="mmlu,arc_challenge,hellaswag,mgsm_native_cot_es,global_mmlu_full_es"

lm_eval \
  --model vllm \
  --model_args pretrained=$MODEL_PATH,dtype=bfloat16,max_model_len=4096 \
  --tasks $TASKS \
  --num_fewshot 5 \
  --batch_size auto \
  --output_path $OUTPUT_DIR/ \
  --log_samples

# IFEval va aparte: siempre 0-shot (no tiene split para few-shot)
lm_eval \
  --model vllm \
  --model_args pretrained=$MODEL_PATH,dtype=bfloat16,max_model_len=4096 \
  --tasks ifeval \
  --num_fewshot 0 \
  --batch_size auto \
  --output_path $OUTPUT_DIR/ \
  --log_samples

# lm_eval escribe $OUTPUT_DIR/<modelo_sanitizado>/results_<fecha>.json
echo "Evaluación terminada:"; ls -t $OUTPUT_DIR/*/results_*.json

4. Crear un task personalizado

Para benchmarks de opción múltiple (ej. LatamQA) se crea un YAML de configuración; no hace falta tocar código Python. LatamQA (inria-chile/latamqa_mcq_es-la) trae una respuesta correcta y tres distractores escritos como oraciones completas, así que conviene puntuarlo en formato cloze: el modelo asigna log-verosimilitud a cada opción completa y no hay letras A/B/C/D que sesguen por posición.

yaml — tasks/latamqa_es/latamqa_es.yaml
task: latamqa_es
dataset_path: inria-chile/latamqa_mcq_es-la   # LatamQA, español latinoamericano
test_split: train            # el dataset solo publica el split "train"
output_type: multiple_choice
doc_to_text: "Pregunta: {{question}}\nRespuesta:"
doc_to_choice: "{{[answer, distractor1, distractor2, distractor3]}}"
doc_to_target: 0             # índice de la opción correcta en doc_to_choice
metric_list:
  - metric: acc
    aggregation: mean
    higher_is_better: true
  - metric: acc_norm
    aggregation: mean
    higher_is_better: true
num_fewshot: 0
# Si tu benchmark tiene otro split y quieres few-shot, define de dónde salen los
# ejemplos para no sacarlos del propio test (contaminación de la evaluación):
# fewshot_split: validation
# fewshot_config:
#   sampler: first_n
bash — correr el task custom
lm_eval \
  --model vllm \
  --model_args pretrained=models/mi-modelo-es \
  --tasks latamqa_es \
  --include_path tasks/latamqa_es \
  --output_path resultados/latamqa/

Trueque: preguntas abiertas con LLM-as-a-judge

Trueque (latam-gpt/Trueque-Benchmark-beta-0.1) no es de opción múltiple: son 500 preguntas abiertas sobre países latinoamericanos con una reference_answer, y se evalúa generando la respuesta (generate_until) y pidiéndole a un juez que la compare con la referencia. El esquema mínimo: generas con vLLM y juzgas con otro modelo servido con vllm serve.

python — eval_trueque.py
# pip install vllm openai datasets
# Juez en otra GPU/nodo:  vllm serve Qwen/Qwen3-32B --port 8001
import json
from datasets import load_dataset
from openai import OpenAI
from vllm import LLM, SamplingParams

ds = load_dataset("latam-gpt/Trueque-Benchmark-beta-0.1", split="train")

# 1) Generar respuestas del modelo evaluado (instruct, con chat template)
llm = LLM(model="models/mi-modelo-es", dtype="bfloat16", max_model_len=4096)
convs = [[{"role": "user", "content": q}] for q in ds["question"]]
outs = llm.chat(convs, SamplingParams(temperature=0.0, max_tokens=512))
answers = [o.outputs[0].text.strip() for o in outs]

# 2) Juzgar contra la respuesta de referencia
judge = OpenAI(base_url="http://localhost:8001/v1", api_key="EMPTY")
PROMPT = """Eres un evaluador estricto de exactitud factual.
Pregunta: {q}
Respuesta de referencia: {ref}
Respuesta del modelo: {ans}
¿La respuesta del modelo es correcta y consistente con la referencia?
Responde solo con un JSON: {{"correcta": true}} o {{"correcta": false}}"""

verdicts = []
for row, ans in zip(ds, answers):
    r = judge.chat.completions.create(
        model="Qwen/Qwen3-32B",
        messages=[{"role": "user", "content": PROMPT.format(q=row["question"], ref=row["reference_answer"], ans=ans)}],
        temperature=0.0,
        response_format={"type": "json_object"},
        extra_body={"chat_template_kwargs": {"enable_thinking": False}},  # Qwen3 sin modo thinking
    )
    verdicts.append(bool(json.loads(r.choices[0].message.content).get("correcta", False)))

print(f"Trueque (juez, sin corregir): {sum(verdicts) / len(verdicts):.3f}")
El juez también se equivoca: la tasa cruda del juez está sesgada por sus falsos positivos y negativos. El propio dataset declara seguir a Lee et al. (2025) para corregirlo con un set de calibración anotado por humanos e intervalos de confianza; el paso a paso está en LLM-as-a-judge calibrado, y cómo comparar checkpoints con intervalos y tests pareados en Evaluación estadísticamente rigurosa.

5. Interpretar resultados correctamente

Estructura del JSON de salida

python — leer resultados
import glob
import json
import os

def latest_results(run_dir):
    """Último results_*.json que lm-eval escribió bajo run_dir/<modelo_sanitizado>/."""
    files = glob.glob(os.path.join(run_dir, "**", "results_*.json"), recursive=True)
    if not files:
        raise FileNotFoundError(f"No hay results_*.json bajo {run_dir}")
    return max(files, key=os.path.getmtime)

with open(latest_results("resultados/run1/")) as f:
    results = json.load(f)

# Accuracy por task
for task, metrics in results["results"].items():
    acc = metrics.get("acc,none", metrics.get("acc_norm,none"))
    if acc is None:
        # tareas generativas usan otras claves, p.ej. MGSM "exact_match,flexible-extract"
        # e IFEval "prompt_level_strict_acc,none"
        print(f"{task}: {metrics}")
        continue
    stderr = metrics.get("acc_stderr,none", metrics.get("acc_norm_stderr,none", 0))
    stderr = stderr if isinstance(stderr, (int, float)) else float("nan")  # los grupos pueden traer "N/A"
    print(f"{task}: {acc:.3f} ± {stderr:.3f}")

# Comparar dos modelos
import pandas as pd

def load_results(run_dir):
    with open(latest_results(run_dir)) as f:
        data = json.load(f)
    return {task: m.get("acc,none", m.get("acc_norm,none"))
            for task, m in data["results"].items()}

base   = load_results("resultados/baseline/")
tuned  = load_results("resultados/finetuned/")
df = pd.DataFrame({"baseline": base, "finetuned": tuned})
df["delta"] = df["finetuned"] - df["baseline"]
print(df.sort_values("delta", ascending=False))
Errores comunes de reporting:
  • Reportar solo los mejores resultados entre varias ejecuciones (cherry-picking)
  • No reportar el número de few-shot shots usados
  • Comparar modelos evaluados con prompts diferentes
  • Usar acc vs acc_norm inconsistentemente — acc_norm penaliza por longitud de opción

El ± stderr de lm-eval es solo el punto de partida: para decidir si un checkpoint realmente mejora necesitas intervalos de confianza y tests pareados por ítem (ver Evaluación estadísticamente rigurosa). Si además quieres una suite multilingüe con tareas es/pt listas para usar (incluido PoETa v2 para portugués), revisa Evaluación multilingüe con lighteval.

6. Detección de contaminación

La contaminación ocurre cuando los datos de evaluación aparecen en el training set. Puede inflar scores 5–15 puntos. Detectarla con n-gram overlap, pero en la dirección correcta: el set pequeño es el del benchmark (decenas de miles de ítems), no el del corpus. Se indexan los n-gramas del benchmark (pregunta + opciones, hasheados) y se recorre el corpus en streaming chequeando pertenencia, con memoria acotada:

python — contamination_check.py
import hashlib
import re
from collections import defaultdict
from datasets import load_dataset

N = 8  # 13 es el estándar en papers, pero muchas preguntas de MMLU tienen menos de 13 palabras

def tokens(text):
    return re.findall(r"\w+", text.lower())

def hashed_ngrams(toks, n=N):
    for i in range(len(toks) - n + 1):
        yield hashlib.blake2b(" ".join(toks[i:i + n]).encode(), digest_size=8).digest()

# 1) Índice pequeño: n-grama del benchmark → ítems que lo contienen
benchmark = load_dataset("cais/mmlu", "all", split="test")
index = defaultdict(set)
for idx, item in enumerate(benchmark):
    text = item["question"] + " " + " ".join(item["choices"])
    for h in hashed_ngrams(tokens(text)):
        index[h].add(idx)

# 2) Recorrer el corpus en streaming (muestra de 1M docs) sin guardar sus n-gramas
corpus = load_dataset("HuggingFaceFW/fineweb", name="sample-10BT", split="train", streaming=True)
contaminated = set()
for i, doc in enumerate(corpus):
    if i >= 1_000_000:
        break
    for h in hashed_ngrams(tokens(doc["text"])):
        if h in index:
            contaminated.update(index[h])

print(f"Posible contaminación: {len(contaminated)}/{len(benchmark)} "
      f"({100 * len(contaminated) / len(benchmark):.1f}%)")
Para es/pt: corre el mismo chequeo contra tus benchmarks locales (LatamQA, Trueque, Global-MMLU es/pt) y contra tu corpus real de pretraining, no solo FineWeb. Los ítems marcados se excluyen del reporte o se reportan aparte; con 8-gramas habrá falsos positivos en frases genéricas, así que revisa una muestra a mano.
