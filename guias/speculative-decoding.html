Speculative Decoding: 2-3× más rápido sin perder calidad

Un modelo pequeño (draft) propone tokens, el modelo grande (target) los verifica en paralelo. La distribución de salida es idéntica al modelo original — sin ninguna degradación de calidad.

1. Cómo funciona

La observación clave: el cuello de botella de LLM inference no es la computación, sino la latencia de memoria (leer pesos del modelo en cada paso). Speculative decoding amortiza esto verificando K tokens en un solo forward pass del modelo grande.

El loop básico:

  1. El draft model (pequeño, rápido) genera K tokens autoregressivamente: t₁, t₂, …, tₖ
  2. El target model (grande) recibe el contexto + los K tokens propuestos y calcula probabilidades para K+1 posiciones en un solo forward pass
  3. Se acepta o rechaza cada token propuesto mediante muestreo de rechazo (rejection sampling)
  4. Los tokens aceptados se añaden a la secuencia; el primer rechazado se reemplaza con una muestra del target

Propiedad fundamental: La distribución de tokens generados es matemáticamente idéntica a la del target model solo. No hay trade-off de calidad — solo velocidad.

SituaciónSpeedupPor qué
Draft muy alineado con target (texto repetitivo, código)2-4×Casi todos los tokens se aceptan
Texto creativo / aleatorio1.2-1.8×Muchos rechazos
Batch grande (≥16 requests)~1× o menos (draft clásico)El target pasa a estar limitado por cómputo; EAGLE-3/MTP conservan algo de ganancia a batch moderado
La ganancia es máxima con batch size pequeño (1-4 requests) y decrece al aumentar la concurrencia: con muchas requests simultáneas el target deja de estar limitado por memoria y verificar tokens rechazados cuesta cómputo. Con un draft model clásico, a batch grande suele no dar ventaja; métodos livianos como EAGLE-3 o MTP mantienen ganancias a batch moderado. Mide siempre con tu carga real antes de activarlo en producción.

2. Speculative Decoding con vLLM (producción)

vLLM (V1) tiene soporte nativo y se configura con un único flag --speculative-config (JSON) cuyo campo method elige la técnica: draft_model, ngram, eagle3, mtp, entre otros. Los flags antiguos (--speculative-model, --num-speculative-tokens) ya no existen. Para el resto de la configuración de serving ver la guía Serving en producción.

bash
# Draft model clásico (mismo tokenizer que el target, p.ej. un SFT sobre Llama 3.1 8B)
vllm serve <TU_ORG>/<modelo-8b-sft> \
  --dtype bfloat16 \
  --max-model-len 8192 \
  --speculative-config '{"method": "draft_model", "model": "meta-llama/Llama-3.2-1B-Instruct", "num_speculative_tokens": 5, "draft_tensor_parallel_size": 1}'

# N-gramas (prompt lookup): sin segundo modelo
vllm serve <TU_ORG>/<modelo-8b-sft> \
  --speculative-config '{"method": "ngram", "num_speculative_tokens": 4, "prompt_lookup_min": 2, "prompt_lookup_max": 5}'

3. Con transformers (prototipado)

python
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

TARGET_MODEL = "<TU_ORG>/<modelo-8b-sft>"  # basado en Llama 3.x (mismo tokenizer que el draft)
DRAFT_MODEL  = "meta-llama/Llama-3.2-1B-Instruct"

target_tok = AutoTokenizer.from_pretrained(TARGET_MODEL)
target = AutoModelForCausalLM.from_pretrained(
    TARGET_MODEL, dtype=torch.bfloat16, device_map="cuda:0"
)

draft = AutoModelForCausalLM.from_pretrained(
    DRAFT_MODEL, dtype=torch.bfloat16, device_map="cuda:0"
)

messages = [{"role": "user", "content": "Explica la atención multi-cabeza."}]
enc = target_tok.apply_chat_template(
    messages, add_generation_prompt=True, return_dict=True, return_tensors="pt"
).to("cuda:0")
input_ids = enc["input_ids"]

# Speculative decoding: assistant_model = draft model
output = target.generate(
    **enc,
    assistant_model=draft,        # ← activa speculative decoding
    max_new_tokens=256,
    do_sample=False,
)

print(target_tok.decode(output[0][input_ids.shape[1]:], skip_special_tokens=True))

Prompt lookup decoding (sin draft model separado)

Una variante más sencilla: buscar n-gramas en el prompt que coincidan con los últimos tokens y usarlos como "draft". Útil para documentos largos con repeticiones (código, JSON, traducciones).

python
# Continúa el bloque anterior (target, enc)
output = target.generate(
    **enc,
    prompt_lookup_num_tokens=10,  # ← sin draft model, busca en el prompt
    max_new_tokens=256,
    do_sample=False,
)

4. EAGLE-3 y MTP (sin modelo draft separado)

En vez de un segundo LLM completo, estos métodos usan cabezas livianas que reutilizan las representaciones internas del target para proponer tokens. Son hoy la opción por defecto en serving y conservan ganancias a batch moderado.

  • EAGLE-3: una cabeza de draft (~1 capa de decoder) que se alimenta de features de varias capas del target. Requiere entrenar la cabeza para el modelo concreto; para modelos públicos suele haber cabezas ya publicadas (p.ej. RedHatAI/Llama-3.1-8B-Instruct-speculator.eagle3).
  • MTP (Multi-Token Prediction): el modelo se preentrena con módulos que predicen varios tokens futuros (DeepSeek-V3, MiMo, etc.); vLLM los reutiliza como draft. Solo funciona en familias de modelos con cabezas MTP soportadas por vLLM.
bash
# EAGLE-3: target Llama 3.1 8B Instruct + cabeza EAGLE-3 publicada
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --speculative-config '{"method": "eagle3", "model": "RedHatAI/Llama-3.1-8B-Instruct-speculator.eagle3", "num_speculative_tokens": 3}'

# MTP: modelo con cabezas MTP nativas
vllm serve XiaomiMiMo/MiMo-7B-Base \
  --speculative-config '{"method": "mtp", "num_speculative_tokens": 1}'
Contexto histórico — Medusa: Medusa (Cai et al., 2024) fue la primera propuesta popular de cabezas de predicción sobre el propio target (cada cabeza predice la posición t+k, con verificación en árbol). El proyecto FasterDecoding/Medusa está inactivo y fue superado por EAGLE-3 y MTP, que vLLM soporta nativamente. Para LatamGPT: si se tiene un checkpoint SFT propio, se puede entrenar una cabeza EAGLE-3 sobre datos en español/portugués (p.ej. con el proyecto speculators de vLLM) y servirla con method: eagle3.

5. Medir el speedup real

python
import time
import torch

def benchmark_generate(model, tokenizer, prompt: str,
                        n_tokens: int = 200,
                        draft_model=None) -> dict:
    input_ids = tokenizer(prompt, return_tensors="pt").input_ids.to(model.device)

    kwargs = dict(max_new_tokens=n_tokens, do_sample=False)
    if draft_model is not None:
        kwargs["assistant_model"] = draft_model

    # Warmup
    with torch.no_grad():
        model.generate(input_ids=input_ids, **{**kwargs, "max_new_tokens": 10})

    torch.cuda.synchronize()
    t0 = time.perf_counter()
    with torch.no_grad():
        out = model.generate(input_ids=input_ids, **kwargs)
    torch.cuda.synchronize()
    elapsed = time.perf_counter() - t0

    n_gen = out.shape[1] - input_ids.shape[1]
    return {"tok/s": n_gen / elapsed, "elapsed": elapsed, "n_tokens": n_gen}

# Continúa el bloque de la sección 3 (target, target_tok, draft)
PROMPT = "Explica detalladamente cómo funciona el algoritmo Transformer, incluyendo la atención multi-cabeza, las capas feed-forward y la normalización de capas."

r_baseline = benchmark_generate(target, target_tok, PROMPT)
r_speculative = benchmark_generate(target, target_tok, PROMPT, draft_model=draft)

print(f"Baseline:    {r_baseline['tok/s']:.1f} tok/s")
print(f"Speculative: {r_speculative['tok/s']:.1f} tok/s")
print(f"Speedup:     {r_speculative['tok/s'] / r_baseline['tok/s']:.2f}×")

6. Cuándo usar y cuándo no

Caso de usoRecomendaciónPor qué
Chat interactivo (batch=1)Speculative decoding ✓Latencia percibida mejora ~2×
Evaluación de modelos (lm-eval)Prompt lookup ✓Sin segundo modelo, gain moderado
Servidor con 50+ requests/sEvitar draft clásico; medir EAGLE-3/MTPTarget saturado; el overhead del draft pesa más
Generación de datos sintéticosDepende del batchCon temperatura > 0 el muestreo por rechazo preserva la distribución, pero baja la aceptación; en generación masiva (batch grande) la ganancia suele ser baja
Código / texto repetitivoMuy recomendadoDraft acierta mucho → aceptación alta
