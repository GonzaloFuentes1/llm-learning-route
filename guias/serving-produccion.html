Serving en producción con vLLM V1 y SGLang

Del endpoint de prueba a un servicio que aguanta tráfico real en español y portugués: configuración reproducible en YAML, prefix caching medido, JSON garantizado con structured outputs, tool calling y modelos de razonamiento, varios LoRA sobre un mismo modelo base, EAGLE-3, el mismo stack en SGLang, benchmarks con SLOs (vllm bench serve y GuideLLM), capacity planning y despliegue en Slurm con Prometheus.

1. Qué cambia al pasar a producción

Esta guía asume que ya levantaste un servidor con la guía básica Serving con vLLM: primeros pasos (instalación, vllm serve, cliente OpenAI, /metrics). Aquí resolvemos lo que aparece cuando el servidor deja de ser tuyo y pasa a atender usuarios: latencia estable bajo carga, respuestas parseables, varias variantes del modelo, costo por token y operación en el cluster.

2. Tres entornos: vLLM, SGLang y cliente

vLLM y SGLang fijan versiones distintas de PyTorch y de los backends de gramáticas (xgrammar, llguidance), así que cada motor vive en su propio entorno. Los clientes y benchmarks van en un tercero, que no necesita GPU y puede correr en otra máquina para no robarle CPU al servidor.

bash — instalación
# vLLM: binarios CUDA 12.9 por defecto (variantes 12.8 y 13.0), compute capability >= 7.5
uv venv ~/envs/vllm --python 3.12 --seed
VIRTUAL_ENV=~/envs/vllm uv pip install vllm --torch-backend=auto

# SGLang: exige un driver compatible con CUDA 13
uv venv ~/envs/sglang --python 3.12 --seed
VIRTUAL_ENV=~/envs/sglang uv pip install --prerelease=allow sglang

# Cliente y benchmarks (sin GPU)
uv venv ~/envs/client --python 3.12 --seed
VIRTUAL_ENV=~/envs/client uv pip install openai pydantic pandas transformers "guidellm[recommended]"

# En el cluster, las imágenes oficiales evitan compilar nada
apptainer pull vllm.sif docker://vllm/vllm-openai:latest
apptainer pull sglang.sif docker://lmsysorg/sglang:latest
No actualices los backends por separado: vLLM fija rangos de xgrammar y llguidance. Un pip install -U xgrammar en el entorno del servidor rompe structured outputs de forma silenciosa o al arrancar.

3. Configuración reproducible con vllm serve --config

En producción los flags viven en un YAML versionado junto al código, no en el historial de la terminal. Los argumentos de la línea de comandos tienen prioridad sobre el archivo, lo que permite cambiar el puerto o agregar LoRA sin duplicar la configuración.

bash — serve_vllm.yaml y arranque
cat > serve_vllm.yaml <<'EOF'
served-model-name: latam-chat

port: 8000
max-model-len: 16384
gpu-memory-utilization: 0.90
max-num-seqs: 64
max-num-batched-tokens: 8192
kv-cache-dtype: auto
enable-prefix-caching: true
reasoning-parser: qwen3
enable-auto-tool-choice: true
tool-call-parser: hermes
EOF

# La API key va por variable de entorno, nunca en el YAML
export VLLM_API_KEY="$(openssl rand -hex 24)"

Para dimensionar, calcula cuánto KV cache ocupa cada token y cuántos tokens simultáneos caben. Este script lee la configuración del modelo desde el Hub:

python — kv_budget.py
from transformers import AutoConfig

MODEL = "Qwen/Qwen3-8B"
GPU_GB = 80            # VRAM de la GPU
UTIL = 0.90            # gpu-memory-utilization
PARAMS_B = 8.2         # parámetros en miles de millones
WEIGHT_BYTES = 2       # BF16 = 2, FP8 = 1, W4A16 ~ 0.55
KV_BYTES = 2           # kv-cache-dtype auto (BF16) = 2, fp8 = 1
OVERHEAD_GB = 3        # activaciones, CUDA graphs, fragmentación

cfg = AutoConfig.from_pretrained(MODEL)
head_dim = getattr(cfg, "head_dim", None) or cfg.hidden_size // cfg.num_attention_heads
kv_per_token = 2 * cfg.num_hidden_layers * cfg.num_key_value_heads * head_dim * KV_BYTES

weights_gb = PARAMS_B * WEIGHT_BYTES
kv_gb = GPU_GB * UTIL - weights_gb - OVERHEAD_GB
tokens = int(kv_gb * 1e9 / kv_per_token)

print(f"KV/token: {kv_per_token / 1024:.0f} KiB | pesos: {weights_gb:.1f} GB | KV: {kv_gb:.1f} GB | ~{tokens:,} tokens")
for ctx in (2048, 4096, 8192, 16384):
    print(f"  conversaciones simultáneas de {ctx:>5} tokens: ~{tokens // ctx}")
Ángulo es/pt: calcula los contextos con tokens reales de tus conversaciones en español y portugués. Si tu tokenizer gasta 20-30% más tokens por palabra que en inglés, la misma conversación ocupa 20-30% más KV cache y la concurrencia real baja en la misma proporción.

4. Prefix caching en la práctica

vLLM V1 tiene activado por defecto el Automatic Prefix Caching: el KV cache se guarda en bloques identificados por un hash de su contenido y del prefijo anterior, así que dos requests que comparten los primeros N tokens reutilizan esos bloques y se saltan su prefill. SGLang hace lo mismo con RadixAttention, un árbol radix de prefijos con desalojo LRU. En ambos casos solo se reutiliza el prefijo exacto: un token distinto al inicio invalida todo lo que viene después.

HazEvita
System prompt, reglamento, catálogo o few-shots fijos al comienzoFecha, hora, nombre del usuario o ID de sesión en la primera línea del system prompt
Contexto variable (documentos de RAG, pregunta) al finalReordenar los documentos recuperados en cada turno si no cambió la consulta
Un system prompt por idioma (es, pt) estable en el tiempoTraducir o reformular el system prompt en cada request

El script manda 300 consultas que comparten un reglamento académico largo en español como system prompt y mide TTFT p50/p99 y la tasa de acierto en /metrics. Córrelo dos veces: con el servidor normal y con el servidor arrancado con --no-enable-prefix-caching.

python — prefix_cache_bench.py
import asyncio
import os
import statistics
import time
import urllib.request

from openai import AsyncOpenAI

BASE = os.environ.get("BASE_URL", "http://127.0.0.1:8000")
MODEL = os.environ.get("MODEL", "latam-chat")
N_REQUESTS, CONCURRENCY = 300, 32

client = AsyncOpenAI(base_url=f"{BASE}/v1", api_key=os.environ.get("VLLM_API_KEY", "EMPTY"))

REGLAMENTO = "\n".join(
    f"Artículo {i}. Las solicitudes de tipo {i % 7} se resuelven en un plazo de {5 + i % 10} "
    f"días hábiles y requieren el formulario F-{100 + i}, firmado por la jefatura de carrera."
    for i in range(1, 151)
)  # ~4.000 tokens de prefijo compartido
SYSTEM = ("Eres el asistente de la secretaría académica. Responde en español de Chile, en dos "
          "frases, citando el artículo del reglamento que aplica.\n\n" + REGLAMENTO)


def scrape() -> dict[str, float]:
    text = urllib.request.urlopen(f"{BASE}/metrics", timeout=5).read().decode()
    out: dict[str, float] = {}
    for line in text.splitlines():
        if line and not line.startswith("#"):
            name, _, value = line.rpartition(" ")
            key = name.split("{", 1)[0]
            out[key] = out.get(key, 0.0) + float(value)
    return out


async def one(i: int, sem: asyncio.Semaphore) -> float | None:
    async with sem:
        t0 = time.perf_counter()
        stream = await client.chat.completions.create(
            model=MODEL,
            messages=[{"role": "system", "content": SYSTEM},
                      {"role": "user", "content": f"Consulta {i}: ¿qué plazo tiene una solicitud de tipo {i % 7}?"}],
            max_tokens=64,
            stream=True,
            extra_body={"chat_template_kwargs": {"enable_thinking": False}},
        )
        ttft = None
        async for chunk in stream:
            delta = chunk.choices[0].delta if chunk.choices else None
            if ttft is None and delta and (delta.content or getattr(delta, "reasoning", None)):
                ttft = time.perf_counter() - t0  # primer token visible
        return ttft


async def main() -> None:
    before = scrape()
    sem = asyncio.Semaphore(CONCURRENCY)
    ttfts = await asyncio.gather(*(one(i, sem) for i in range(N_REQUESTS)))
    after = scrape()
    ttfts = sorted(t for t in ttfts if t is not None)
    q = after.get("vllm:prefix_cache_queries_total", 0) - before.get("vllm:prefix_cache_queries_total", 0)
    h = after.get("vllm:prefix_cache_hits_total", 0) - before.get("vllm:prefix_cache_hits_total", 0)
    p99 = statistics.quantiles(ttfts, n=100)[98]
    print(f"TTFT p50={statistics.median(ttfts) * 1000:.0f} ms | p99={p99 * 1000:.0f} ms")
    print(f"prefix cache hit rate: {h / q:.1%}" if q else "sin métricas de prefix cache")


asyncio.run(main())
Qué esperar: con el caché activo la tasa de acierto debería rondar el 90% o más (solo la pregunta final es nueva; los primeros requests concurrentes todavía no encuentran el prefijo en caché) y el TTFT p50 caer varias veces respecto a la corrida sin caché, porque el prefill de ~4.000 tokens se hace una sola vez. Si el acierto es bajo, busca qué cambia al inicio del prompt.

5. Structured outputs: JSON garantizado

Pedir "responde solo JSON" en el prompt funciona casi siempre, que en producción significa que falla todos los días. Con decoding restringido el motor enmascara en cada paso los tokens que violarían el schema, así que la salida es parseable por construcción. vLLM usa xgrammar o guidance según el schema (--structured-outputs-config.backend auto por defecto); SGLang se configura con --grammar-backend xgrammar. Desde vLLM v0.12.0 los campos guided_json, guided_regex, guided_choice y similares ya no existen.

python — client_structured.py
import os
from typing import Literal

from openai import OpenAI
from pydantic import BaseModel, Field, ValidationError

client = OpenAI(base_url=os.environ.get("BASE_URL", "http://127.0.0.1:8000") + "/v1",
                api_key=os.environ.get("VLLM_API_KEY", "EMPTY"))
MODEL = os.environ.get("MODEL", "latam-chat")
NO_THINK = {"chat_template_kwargs": {"enable_thinking": False}}


class Monto(BaseModel):
    valor: float
    moneda: Literal["CLP", "BRL", "ARS", "MXN", "COP", "PEN", "USD"]


class Noticia(BaseModel):
    personas: list[str]
    organizaciones: list[str]
    pais: Literal["Chile", "Brasil", "Argentina", "México", "Colombia", "Perú", "Otro"]
    fecha: str | None = Field(None, description="AAAA-MM-DD si aparece en el texto")
    montos: list[Monto]
    identificadores: list[str] = Field(default_factory=list, description="RUT, CPF o CUIT tal como aparecen")


NOTICIAS = [  # textos ficticios
    "Santiago, 3 de marzo de 2026. La cooperativa Agua Clara, RUT 76.123.456-7, recibió un aporte "
    "de $450 millones de pesos del Gobierno Regional, informó su presidenta, Marta Rojas.",
    "São Paulo, 12/05/2026 - A startup Pagamentos Sul captou R$ 18 milhões em rodada liderada pelo "
    "fundo Ipê Capital. O fundador, João Almeida (CPF 123.456.789-09), disse que vai contratar 40 pessoas.",
]
INSTRUCCION = "Extrae las entidades de la noticia como JSON con los campos del schema."
schema_fmt = {"type": "json_schema",
              "json_schema": {"name": "noticia", "schema": Noticia.model_json_schema()}}


def extraer(texto: str, restringido: bool) -> str:
    kwargs = {"response_format": schema_fmt} if restringido else {}
    resp = client.chat.completions.create(
        model=MODEL, temperature=0.7, max_tokens=512, extra_body=NO_THINK,
        messages=[{"role": "system", "content": INSTRUCCION + " Responde solo con JSON."},
                  {"role": "user", "content": texto}],
        **kwargs,
    )
    return resp.choices[0].message.content or ""


for restringido in (False, True):
    validos = 0
    for _ in range(10):  # 10 muestras por noticia con temperature 0.7
        for texto in NOTICIAS:
            try:
                Noticia.model_validate_json(extraer(texto, restringido))
                validos += 1
            except ValidationError:
                pass
    print(f"restringido={restringido}: {validos}/{10 * len(NOTICIAS)} JSON válidos")

print(Noticia.model_validate_json(extraer(NOTICIAS[1], True)).model_dump_json(indent=2))

# Otras restricciones de vLLM van en extra_body["structured_outputs"]
idioma = client.chat.completions.create(
    model=MODEL, max_tokens=5,
    messages=[{"role": "user", "content": f"¿En qué idioma está este texto? {NOTICIAS[1]}"}],
    extra_body={**NO_THINK, "structured_outputs": {"choice": ["es", "pt", "otro"]}},
)
rut = client.chat.completions.create(
    model=MODEL, max_tokens=20,
    messages=[{"role": "user", "content": f"Copia el RUT que aparece aquí: {NOTICIAS[0]}"}],
    extra_body={**NO_THINK, "structured_outputs": {"regex": r"\d{1,2}\.\d{3}\.\d{3}-[0-9kK]"}},
)
print(idioma.choices[0].message.content, rut.choices[0].message.content)
El schema restringe la forma, no la verdad: el decoding restringido garantiza un RUT con formato válido, no que el RUT exista o que el dígito verificador sea correcto. Valida el contenido después (dígito verificador del RUT, CPF y CUIT) y mide la exactitud de la extracción con un set anotado en es/pt.
Razonamiento + JSON: con --reasoning-parser, vLLM aplica la restricción solo a la respuesta final, después del bloque de razonamiento. Si la tarea es extracción simple, desactiva el thinking (enable_thinking: False) y ahorras cientos de tokens por request.

6. Tool calling y modelos de razonamiento

Con enable-auto-tool-choice y tool-call-parser hermes (ya en el YAML de la sección 3) el servidor devuelve tool_calls en formato OpenAI. Con reasoning-parser qwen3 el razonamiento llega en message.reasoning (antes se llamaba reasoning_content, nombre que todavía puedes recibir de SGLang u otros servidores). El ciclo completo, con una pregunta en portugués:

python — client_tools.py
import json
import os

from openai import OpenAI

client = OpenAI(base_url=os.environ.get("BASE_URL", "http://127.0.0.1:8000") + "/v1",
                api_key=os.environ.get("VLLM_API_KEY", "EMPTY"))
MODEL = os.environ.get("MODEL", "latam-chat")

# Tasas de ejemplo; en producción vendrían de una API o base de datos
TASAS_USD = {"CLP": 940.0, "BRL": 5.4, "ARS": 1200.0, "MXN": 18.5, "USD": 1.0}


def tipo_de_cambio(monto: float, origen: str, destino: str) -> dict:
    resultado = monto / TASAS_USD[origen] * TASAS_USD[destino]
    return {"monto": monto, "origen": origen, "destino": destino, "resultado": round(resultado, 2)}


TOOLS = [{
    "type": "function",
    "function": {
        "name": "tipo_de_cambio",
        "description": "Convierte un monto entre monedas latinoamericanas y USD.",
        "parameters": {
            "type": "object",
            "properties": {
                "monto": {"type": "number"},
                "origen": {"type": "string", "enum": list(TASAS_USD)},
                "destino": {"type": "string", "enum": list(TASAS_USD)},
            },
            "required": ["monto", "origen", "destino"],
        },
    },
}]

messages = [
    {"role": "system", "content": "Responda em português do Brasil. Use as ferramentas quando precisar de números."},
    {"role": "user", "content": "Quanto são 500 reais em pesos chilenos?"},
]

for _ in range(3):  # como máximo 3 rondas de herramientas
    msg = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS,
                                         tool_choice="auto", max_tokens=1024).choices[0].message
    razonamiento = getattr(msg, "reasoning", None) or getattr(msg, "reasoning_content", None)
    if razonamiento:
        print("[razonamiento]", razonamiento[:300], "...")
    if not msg.tool_calls:
        print("[respuesta]", msg.content)
        break
    messages.append({"role": "assistant", "content": msg.content or "",
                     "tool_calls": [tc.model_dump() for tc in msg.tool_calls]})
    for tc in msg.tool_calls:
        args = json.loads(tc.function.arguments)
        resultado = tipo_de_cambio(**args)
        print("[tool]", tc.function.name, args, "→", resultado)
        messages.append({"role": "tool", "tool_call_id": tc.id, "content": json.dumps(resultado)})
No reenvíes el razonamiento: el chat template de Qwen3 descarta el <think> de turnos anteriores; por eso el mensaje del asistente que se agrega al historial lleva solo content y tool_calls. Para agentes más complejos (MCP, varias herramientas, evaluación) sigue con la guía Agentes con tool calling y MCP sobre vLLM.

7. Multi-LoRA: una variante por país sobre el mismo modelo

Si entrenaste adaptadores con la guía de LoRA fine-tuning (por ejemplo, uno para español de Chile y otro para portugués de Brasil), no necesitas una GPU por variante: vLLM sirve el modelo base una vez y aplica el adaptador que pida cada request, mezclando adaptadores distintos en el mismo batch (la técnica de S-LoRA/Punica). El cliente elige la variante con el campo model.

bash — multi_lora.sh
# Permite cargar y descargar adaptadores sin reiniciar (solo en redes de confianza)
export VLLM_ALLOW_RUNTIME_LORA_UPDATING=True
# max-lora-rank debe ser >= al rango del adaptador más grande
vllm serve Qwen/Qwen3-8B --config serve_vllm.yaml \
  --enable-lora \
  --max-loras 4 \
  --max-lora-rank 64 \
  --lora-modules '{"name": "latam-es-cl", "path": "/models/lora/qwen3-8b-es-cl", "base_model_name": "Qwen/Qwen3-8B"}'

# En otra terminal: cargar en caliente el adaptador pt-BR (protegido por la API key: ruta /v1)
curl -X POST http://127.0.0.1:8000/v1/load_lora_adapter \
  -H "Authorization: Bearer $VLLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"lora_name": "latam-pt-br", "lora_path": "/models/lora/qwen3-8b-pt-br"}'

# Deben aparecer latam-chat (base), latam-es-cl y latam-pt-br
curl -s -H "Authorization: Bearer $VLLM_API_KEY" http://127.0.0.1:8000/v1/models | python -m json.tool

El cliente no cambia: model="latam-es-cl" o model="latam-pt-br" elige el adaptador y model="latam-chat" usa el modelo base, todo contra el mismo servidor y en el mismo batch.

Costos ocultos: --max-loras reserva memoria por adaptador activo y los kernels LoRA agregan latencia; mide con el benchmark de la sección 10 con y sin --enable-lora. Y la carga en caliente acepta rutas arbitrarias: no expongas /v1/load_lora_adapter fuera del cluster (filtra la ruta en el proxy, sección 12). En SGLang el equivalente es --enable-lora --lora-paths latam-es-cl=/models/lora/qwen3-8b-es-cl con --max-loras-per-batch, y el cliente pide model="<modelo-base>:latam-es-cl".

8. Speculative decoding con EAGLE-3

Un drafter EAGLE-3 propone varios tokens por paso usando los estados ocultos del modelo y el modelo grande los verifica en una sola pasada: menos latencia entre tokens sin cambiar la distribución de salida. Se configura con --speculative-config (los flags --speculative-model y --num-speculative-tokens son de versiones antiguas). La teoría y otras variantes (n-gram, MTP, draft model) están en la guía de speculative decoding.

bash — spec_decode.sh
vllm serve Qwen/Qwen3-8B --config serve_vllm.yaml \
  --speculative-config '{"method": "eagle3", "model": "RedHatAI/Qwen3-8B-speculator.eagle3", "num_speculative_tokens": 3}'

# Sin modelo extra: n-gram sobre el propio prompt (útil en RAG y edición de texto)
# vllm serve Qwen/Qwen3-8B --config serve_vllm.yaml \
#   --speculative-config '{"method": "ngram", "num_speculative_tokens": 4, "prompt_lookup_max": 4}'

Los drafters públicos se entrenan sobre todo con conversaciones en inglés. Antes de activarlo, mide la aceptación en tus idiomas con los contadores vllm:spec_decode_num_draft_tokens, vllm:spec_decode_num_accepted_tokens y vllm:spec_decode_num_drafts:

python — spec_acceptance.py
import os
import urllib.request

from openai import OpenAI

BASE = "http://127.0.0.1:8000"
client = OpenAI(base_url=f"{BASE}/v1", api_key=os.environ.get("VLLM_API_KEY", "EMPTY"))
PROMPTS = {
    "en": ["Explain how vaccines train the immune system.", "Summarize the causes of inflation."],
    "es": ["Explica cómo las vacunas entrenan al sistema inmune.", "Resume las causas de la inflación."],
    "pt": ["Explique como as vacinas treinam o sistema imunológico.", "Resuma as causas da inflação."],
}
KEYS = ["vllm:spec_decode_num_draft_tokens_total", "vllm:spec_decode_num_accepted_tokens_total",
        "vllm:spec_decode_num_drafts_total"]


def scrape() -> dict[str, float]:
    text = urllib.request.urlopen(f"{BASE}/metrics", timeout=5).read().decode()
    out = dict.fromkeys(KEYS, 0.0)
    for line in text.splitlines():
        name = line.split("{", 1)[0].split(" ", 1)[0]
        if name in out:
            out[name] += float(line.rpartition(" ")[2])
    return out


for lang, prompts in PROMPTS.items():
    a = scrape()
    for p in prompts * 5:  # secuencial: sin ruido de otros requests
        client.chat.completions.create(model="latam-chat", max_tokens=256, temperature=0,
                                       messages=[{"role": "user", "content": p}],
                                       extra_body={"chat_template_kwargs": {"enable_thinking": False}})
    b = scrape()
    draft, acc, n = (b[k] - a[k] for k in KEYS)
    if not draft:
        raise SystemExit("sin drafts: ¿el servidor se lanzó con --speculative-config?")
    print(f"{lang}: aceptación {acc / draft:.1%} | tokens por paso {1 + acc / n:.2f}")
Si la aceptación cae en es/pt: una diferencia de 10+ puntos frente a inglés se nota en el speedup. Entrena tu propio drafter con speculators (vLLM) o SpecForge (SGLang) sobre conversaciones en español y portugués generadas por tu propio modelo. Y recuerda que el beneficio se concentra en baja concurrencia: con batches grandes el decode deja de estar limitado por memoria y el speedup se reduce.

10. Benchmark con SLOs y capacity planning

La pregunta de producción no es "cuántos tokens/s da la GPU" sino cuántos usuarios atiende cumpliendo el SLO. Eso se mide con percentiles altos y con goodput: requests por segundo que cumplen todas las metas de latencia a la vez.

MétricaQué mideSLO típico de chat
TTFTEspera hasta el primer token (prefill + cola)p99 ≤ 2 s
ITL / TPOTTiempo entre tokens / promedio por token de salidap99 ≤ 60 ms (más rápido que la lectura)
E2ELLatencia total del requestDepende del largo de respuesta; útil para timeouts
GoodputRequests/s que cumplen todos los SLOEl número para dimensionar

Un chequeo de cordura antes de medir: en decode a batch 1 cada token exige leer todos los pesos, así que el techo es aproximadamente ancho de banda HBM / bytes de pesos. Para Qwen3-8B en BF16 (~16,4 GB): ~200 tok/s en H100 (3,35 TB/s), ~120 en A100 80 GB (2 TB/s) y ~18 en L4 (300 GB/s), el doble en FP8. Si mides muy por debajo, hay overhead que investigar.

Barrido de concurrencia con vllm bench serve
bash — bench_sweep.sh
#!/usr/bin/env bash

    --backend vllm \

    --dataset-name custom --dataset-path prompts_es_pt.jsonl \
    --custom-output-len 256 \
    --num-prompts "$n" \
    --max-concurrency "$c" \
    --seed "$c" \
    --percentile-metrics ttft,tpot,itl,e2el \
    --metric-percentiles 50,90,99 \

De la curva a réplicas y costo
python — capacity.py
import glob
import json
import math

import pandas as pd

SLO_TTFT_MS, SLO_ITL_MS = 2000, 60
QPS_OBJETIVO = 12            # requests/s en hora punta
USD_GPU_HORA = 2.5           # tu precio on-prem o nube regional
GPUS_POR_REPLICA = 1

rows = []
for path in glob.glob("results/*_c*.json"):
    r = json.load(open(path, encoding="utf-8"))
    rows.append({k: r.get(k) for k in ("config", "max_concurrency", "request_throughput",
                                       "output_throughput", "p99_ttft_ms", "p99_itl_ms", "request_goodput")})
df = pd.DataFrame(rows).sort_values(["config", "max_concurrency"])
print(df.to_string(index=False))

ok = df[(df["p99_ttft_ms"] <= SLO_TTFT_MS) & (df["p99_itl_ms"] <= SLO_ITL_MS)]
for config, g in ok.groupby("config"):
    best = g.loc[g["max_concurrency"].idxmax()]
    replicas = math.ceil(QPS_OBJETIVO / best["request_throughput"])
    usd_m = USD_GPU_HORA * GPUS_POR_REPLICA / (best["output_throughput"] * 3600) * 1e6
    print(f"{config}: concurrencia máx. bajo SLO = {int(best['max_concurrency'])} | "
          f"{best['request_throughput']:.2f} req/s por réplica → {replicas} réplicas | "
          f"USD {usd_m:.2f} por 1M tokens de salida")
Comparaciones justas: mismo dataset, misma semilla, warmup antes de medir, servidor reiniciado (o vllm bench sweep serve, que resetea los cachés) y el cliente en otra máquina o con CPUs dedicadas. Compara BF16 vs FP8 vs W4A16 (guía de cuantización), con y sin EAGLE-3, y TP=2 contra dos réplicas con TP=1: para modelos que caben en una GPU, las réplicas suelen ganar en throughput y TP gana en latencia.
Ángulo Latam: si el servidor está fuera de la región, la red puede sumar 100-200 ms al TTFT; mide también desde donde están tus usuarios. Y compara el costo por millón de tokens contra las APIs comerciales con tus tokens reales en es/pt, no con precios por token calculados en inglés.

11. Escalar: TP, PP, DP, multi-nodo y disaggregation

EstrategiaFlag (vLLM)Cuándo
Tensor parallel--tensor-parallel-sizeEl modelo no cabe en una GPU; dentro del nodo (NVLink)
Pipeline parallel--pipeline-parallel-sizeNo cabe en un nodo: TP = GPUs por nodo, PP = número de nodos
Data parallel--data-parallel-sizeCabe en una GPU y quieres más throughput (o réplicas detrás de un balanceador)
Expert parallel--enable-expert-parallelMoE grandes: reparte expertos en vez de partir cada uno

Multi-nodo sin Ray: el mismo comando en cada nodo, con --headless en los workers. Dentro de un job Slurm de 2 nodos:

bash — node_serve.sh (lanzado con srun en cada nodo)
#!/usr/bin/env bash
# sbatch: --nodes=2 --gpus-per-node=8 --ntasks-per-node=1 ; luego: srun bash node_serve.sh
set -euo pipefail
HEAD_NODE=$(scontrol show hostnames "$SLURM_JOB_NODELIST" | head -n 1)
HEAD_IP=$(getent hosts "$HEAD_NODE" | awk '{print $1}')
ARGS=(--tensor-parallel-size 8 --pipeline-parallel-size 2
      --nnodes 2 --node-rank "$SLURM_NODEID" --master-addr "$HEAD_IP")
# El nodo 0 sirve la API; los demás solo ejecutan su parte del modelo
[ "$SLURM_NODEID" -eq 0 ] || ARGS+=(--headless)
vllm serve "<TU_ORG>/<modelo-70b>" "${ARGS[@]}" --served-model-name latam-chat --port 8000

Cuando el tráfico mezcla prompts largos (RAG, documentos) con mucha generación, prefill y decode compiten por la misma GPU y el ITL se vuelve errático aunque uses chunked prefill. El siguiente paso es disaggregated serving: GPUs de prefill y de decode separadas que se pasan el KV cache por red, con orquestadores como NVIDIA Dynamo, llm-d o el router de SGLang (--disaggregation-mode prefill|decode). Antes de eso, prueba a extender el KV cache a CPU: muchos usuarios que vuelven a la misma conversación ganan TTFT sin agregar GPUs. Con LMCache instalado en el entorno de vLLM basta agregar --kv-transfer-config '{"kv_connector": "LMCacheConnectorV1", "kv_role": "kv_both"}'.

12. Operación en el cluster: Slurm, Prometheus y proxy

Un job que levanta el servidor, espera a que /health responda y publica la URL en un archivo compartido para que clientes y benchmarks la encuentren:

bash — serve.sbatch
#!/bin/bash
#SBATCH --job-name=latam-chat
#SBATCH --nodes=1
#SBATCH --gpus-per-node=1
#SBATCH --cpus-per-task=16
#SBATCH --mem=64G
#SBATCH --time=24:00:00
#SBATCH --output=logs/%x-%j.out
set -euo pipefail
source ~/envs/vllm/bin/activate
export HF_HOME="/scratch/$USER/hf"
export VLLM_API_KEY="$(cat ~/.secrets/vllm_api_key)"
PORT=$(( 8000 + SLURM_JOB_ID % 1000 ))

vllm serve Qwen/Qwen3-8B --config serve_vllm.yaml --port "$PORT" &
PID=$!

for _ in $(seq 1 90); do
  if curl -sf "http://127.0.0.1:${PORT}/health" > /dev/null; then
    mkdir -p "$HOME/endpoints"
    echo "http://$(hostname -f):${PORT}" > "$HOME/endpoints/latam-chat.url"
    echo "servidor listo en $(hostname -f):${PORT}"
    break
  fi
  kill -0 "$PID" 2> /dev/null || { echo "vllm terminó durante el arranque"; exit 1; }
  sleep 10
done
wait "$PID"

Crea logs/ antes del sbatch (Slurm no lo crea). Prometheus lee /metrics de vLLM y de SGLang (con --enable-metrics); agrega el host:puerto que publica el job a scrape_configs; las alertas mínimas son p99 de TTFT e ITL, vllm:num_requests_waiting creciendo, vllm:kv_cache_usage_perc cerca de 1 y vllm:num_preemptions subiendo.

Seguridad: --api-key solo protege las rutas que empiezan con /v1, /v2, /inference y /cohere; rutas como /invocations quedan abiertas. Expón el servicio solo detrás de un reverse proxy (nginx, Caddy, un API gateway) que termine TLS, permita únicamente /v1/chat/completions, /v1/completions y /v1/models, bloquee /v1/load_lora_adapter y aplique rate limiting por usuario. Para moderar contenido delante y detrás del modelo, sigue con Guardrails en producción con vLLM.
