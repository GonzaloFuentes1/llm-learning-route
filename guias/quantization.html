Cuantización para inferencia: FP8, INT4 y NVFP4 con llm-compressor, y GGUF

El flujo vigente a 2026: llm-compressor genera un checkpoint compressed-tensors que vLLM sirve sin flags extra. Elegimos el formato según la GPU, calibramos con texto en español y portugués, medimos VRAM, throughput y recovery en benchmarks es/pt, y cerramos con GGUF + imatrix para llama.cpp en CPU, Mac o GPUs chicas.

AutoAWQ y AutoGPTQ, que eran la base de esta guía, están archivados: AutoAWQ fue absorbido por llm-compressor (proyecto de vLLM) y transformers ya no soporta AutoGPTQ (su backend GPTQ ahora es GPTQModel). Además, instalar autoawq degradaba transformers a la serie 4.x. Hoy el camino recomendado para servir en GPU es: llm-compressor → checkpoint compressed-tensors → vLLM, que detecta el método desde quantization_config y elige el kernel (Marlin, CUTLASS, Machete) sin --quantization.

El estudio más completo sobre qué formato conviene es Give Me BF16 or Give Me Death (Kurtic et al.): FP8 W8A8 es prácticamente sin pérdida en todos los tamaños, INT8 W8A8 pierde 1-3% bien afinado y W4A16 queda muy competitivo. En costo, W4A16 gana en despliegues síncronos (latencia, pocas peticiones) y en GPUs medianas; W8A8 gana con batching continuo y muchas peticiones concurrentes en GPUs de gama alta.

Regla rápida: ¿H100/L40S/B200 y tráfico alto? FP8_DYNAMIC primero (5 minutos, sin datos). ¿L4/A10/RTX o latencia de un usuario? W4A16 con GPTQ o AWQ. ¿Blackwell y quieres exprimirla? NVFP4. ¿Sin GPU o en Mac? GGUF Q4_K_M con imatrix. BitsAndBytes (NF4) queda para QLoRA, no para servir (ver la guía de LoRA).

3. Dataset de calibración en español y portugués

GPTQ, AWQ y NVFP4 ajustan los pesos para minimizar el error en las activaciones que ven durante la calibración. Los datasets por defecto de los ejemplos (perfectblend, ultrachat_200k) son mayormente en inglés; si el modelo se va a usar en es/pt, conviene que la calibración lo refleje. Mezclamos instrucciones humanas de CohereLabs/aya_dataset (formateadas con el chat template) y texto web de HuggingFaceFW/fineweb-2 (spa_Latn y por_Latn).

python · build_calib.py (entorno 1)
from datasets import Dataset, concatenate_datasets, load_dataset
from transformers import AutoTokenizer

MODEL_ID = "Qwen/Qwen3-8B"        # o tu checkpoint: "<TU_ORG>/<modelo>"
N_SAMPLES = 512                   # 50% instrucciones, 50% web
MAX_LEN = 2048

tok = AutoTokenizer.from_pretrained(MODEL_ID)

# 1. Instrucciones humanas es/pt (aya_dataset: columnas inputs, targets, language)
aya = load_dataset("CohereLabs/aya_dataset", split="train")
aya = aya.filter(lambda ex: ex["language"] in ("Spanish", "Portuguese"))
aya = aya.shuffle(seed=0).select(range(N_SAMPLES // 2))


def chat_to_text(ex):
    messages = [
        {"role": "user", "content": ex["inputs"]},
        {"role": "assistant", "content": ex["targets"]},
    ]
    return {"text": tok.apply_chat_template(messages, tokenize=False)}


aya_text = aya.map(chat_to_text, remove_columns=aya.column_names)

# 2. Texto web es/pt de FineWeb-2 en streaming (no descarga el dataset completo)
web_rows = []
for config in ("spa_Latn", "por_Latn"):
    stream = load_dataset("HuggingFaceFW/fineweb-2", name=config, split="train", streaming=True)
    for ex in stream.shuffle(seed=0, buffer_size=10_000).take(N_SAMPLES // 4):
        web_rows.append({"text": ex["text"]})
web_text = Dataset.from_list(web_rows)

calib = concatenate_datasets([aya_text, web_text]).shuffle(seed=0)

# 3. Versión texto plano: la reutilizamos para el imatrix de llama.cpp (sección 10)
with open("calib_es_pt.txt", "w", encoding="utf-8") as f:
    for text in calib["text"]:
        f.write(text.strip() + "\n\n")

# 4. Versión tokenizada para llm-compressor
#    add_special_tokens=False: el chat template ya incluye los tokens especiales
def tokenize(ex):
    return tok(ex["text"], max_length=MAX_LEN, truncation=True,
               padding=False, add_special_tokens=False)


calib_tok = calib.map(tokenize, remove_columns=["text"])
calib_tok.save_to_disk("calib_es_pt")
print(calib_tok)
Calibración que refleje el uso real: si tienes logs de prompts de tu despliegue (anonimizados, ver la guía de anonimización) o tu propio dataset SFT, úsalos en lugar de aya. Con 256-512 muestras de 2048 tokens es suficiente para GPTQ/AWQ; más muestras rara vez mejoran el recovery y alargan la calibración.

4. FP8 en cinco minutos

FP8_DYNAMIC cuantiza pesos a FP8 por canal y calcula la escala de las activaciones por token en tiempo de inferencia, así que no necesita datos. Es el primer formato que deberías probar en Ada/Hopper/Blackwell.

python · quant_fp8.py (entorno 1)
from transformers import AutoModelForCausalLM, AutoTokenizer

from llmcompressor import oneshot
from llmcompressor.modifiers.quantization import QuantizationModifier

MODEL_ID = "Qwen/Qwen3-8B"
SAVE_DIR = "Qwen3-8B-FP8-dynamic"

model = AutoModelForCausalLM.from_pretrained(MODEL_ID, dtype="auto")
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)

# lm_head queda en BF16: es sensible y pesa poco frente al resto
recipe = QuantizationModifier(targets="Linear", scheme="FP8_DYNAMIC", ignore=["lm_head"])

oneshot(model=model, recipe=recipe)   # sin dataset: no hay calibración

model.save_pretrained(SAVE_DIR, save_compressed=True)
tokenizer.save_pretrained(SAVE_DIR)

Para modelos que se distribuyen con FP8 por bloques (típico en MoE grandes) usa scheme="FP8_BLOCK". En Ampere (A100) vLLM carga el checkpoint FP8 igual, pero lo ejecuta como weight-only (W8A16 con Marlin): ahorras VRAM, no cómputo.

5. INT4 weight-only (W4A16): GPTQ y AWQ

Los dos algoritmos producen el mismo tipo de checkpoint (pesos INT4 en grupos de 128) y vLLM los sirve con kernels Marlin. GPTQ corrige el error capa por capa usando información de segundo orden; AWQ escala los canales más importantes según las activaciones antes de redondear. En llm-compressor ambos calibran capa por capa con onloading secuencial, así que un 8B cabe en una GPU de 24 GB.

GPTQ

    enable_thinking=False,   # Qwen3: sin bloque <think> para una respuesta corta
).to(model.device)

print(tokenizer.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True))

tokenizer.save_pretrained(SAVE_DIR)

MoE: en modelos Mixture of Experts deja fuera los routers (son pequeños y muy sensibles), p. ej. ignore=["lm_head", "re:.*mlp.gate$"], y carga el modelo dentro de with load_context(): (de llmcompressor.utils), que convierte los expertos fusionados en capas Linear cuantizables y habilita offloading. oneshot calibra por defecto todos los expertos con todos los tokens (moe_calibrate_all_experts=True), así que expertos poco elegidos por el router también reciben estadísticas. Revisa los ejemplos de examples/quantizing_moe del repo para tu arquitectura.

6. NVFP4 y MXFP4 para Blackwell

NVFP4 cuantiza pesos y activaciones a FP4 (E2M1) con grupos de 16 elementos y una escala FP8 por grupo, más una escala global por tensor que se calibra. Las Tensor Cores de Blackwell lo ejecutan nativamente, así que reduce memoria y cómputo. MXFP4 (estándar OCP Microscaling) usa grupos de 32 con escala E8M0; es el formato en que se publicaron los expertos de gpt-oss.

python · quant_nvfp4.py (entorno 1)
from datasets import load_from_disk
from transformers import AutoModelForCausalLM, AutoTokenizer

from llmcompressor import oneshot
from llmcompressor.modifiers.quantization import QuantizationModifier

MODEL_ID = "Qwen/Qwen3-8B"
SAVE_DIR = "Qwen3-8B-NVFP4-es-pt"

model = AutoModelForCausalLM.from_pretrained(MODEL_ID, dtype="auto")
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)
ds = load_from_disk("calib_es_pt")

# Para MXFP4 usa scheme="MXFP4"; para solo pesos en FP4, scheme="NVFP4A16"
recipe = QuantizationModifier(targets="Linear", scheme="NVFP4", ignore=["lm_head"])

oneshot(
    model=model,
    dataset=ds,
    recipe=recipe,
    max_seq_length=2048,
    num_calibration_samples=64,    # la escala global converge con pocas muestras
)

model.save_pretrained(SAVE_DIR, save_compressed=True)
tokenizer.save_pretrained(SAVE_DIR)
Sin Blackwell no hay ganancia de cómputo: en Hopper o Ampere, según la versión de vLLM, un checkpoint FP4 se rechaza o se ejecuta como weight-only, sin la aceleración W4A4. Además, W4A4 pierde más calidad que W4A16 en tareas de razonamiento: evalúa siempre (sección 9). Una opción intermedia en MoE es la precisión mixta: expertos en FP4 y atención en FP8, con varios config_groups en la receta.

7. KV cache en FP8

Con contexto largo (RAG con documentos legales, historiales clínicos) la KV cache puede pesar más que los pesos. Guardarla en FP8 la reduce a la mitad y duplica las secuencias concurrentes. Hay dos caminos: calibrar escalas en la receta (kv_cache_scheme) o activarla solo al servir con --kv-cache-dtype fp8.

python · quant_fp8_kv.py (entorno 1)
from datasets import load_from_disk
from transformers import AutoModelForCausalLM, AutoTokenizer

from llmcompressor import oneshot

MODEL_ID = "Qwen/Qwen3-8B"
SAVE_DIR = "Qwen3-8B-FP8-KV-es-pt"

# Pesos y activaciones FP8 estáticos + KV cache FP8 con escalas calibradas
RECIPE = """
quant_stage:
    quant_modifiers:
        QuantizationModifier:
            ignore: ["lm_head"]
            config_groups:
                group_0:
                    weights:
                        num_bits: 8
                        type: float
                        strategy: tensor
                        dynamic: false
                        symmetric: true
                    input_activations:
                        num_bits: 8
                        type: float
                        strategy: tensor
                        dynamic: false
                        symmetric: true
                    targets: ["Linear"]
            kv_cache_scheme:
                num_bits: 8
                type: float
                strategy: tensor
                dynamic: false
                symmetric: true
"""

model = AutoModelForCausalLM.from_pretrained(MODEL_ID, dtype="auto")
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)
ds = load_from_disk("calib_es_pt")

oneshot(model=model, dataset=ds, recipe=RECIPE,
        max_seq_length=2048, num_calibration_samples=512)

model.save_pretrained(SAVE_DIR, save_compressed=True)
tokenizer.save_pretrained(SAVE_DIR)

8. Servir con vLLM y medir throughput

vLLM lee quantization_config del config.json y elige el kernel: no pases --quantization (forzarlo puede impedir que use Marlin). El script levanta cada variante, espera a /health, corre vllm bench serve a varias concurrencias y apaga el servidor.

bash · bench_all.sh (entorno 2)
#!/usr/bin/env bash
set -euo pipefail
MODELS=(Qwen/Qwen3-8B Qwen3-8B-FP8-dynamic Qwen3-8B-W4A16-gptq-es-pt Qwen3-8B-W4A16-awq-es-pt)
mkdir -p bench

for M in "${MODELS[@]}"; do
  NAME=$(basename "$M")
  vllm serve "$M" --max-model-len 4096 --gpu-memory-utilization 0.90 --port 8000 \
    > "bench/${NAME}.server.log" 2>&1 &
  PID=$!
  until curl -sf http://localhost:8000/health > /dev/null; do sleep 5; done

  for C in 1 16 64; do
    vllm bench serve \
      --model "$M" \
      --base-url http://localhost:8000 \
      --dataset-name random \
      --random-input-len 1024 \
      --random-output-len 256 \
      --num-prompts $((C * 8)) \
      --max-concurrency "$C" \
      --percentile-metrics ttft,tpot,itl \
      --save-result --result-dir bench \
      --result-filename "${NAME}_c${C}.json"
  done

  grep -i "memory" "bench/${NAME}.server.log" | head -n 5
  kill "$PID"; wait "$PID" || true
done

Valores orientativos para un 8B en una H100 80 GB (mídelos en tu hardware; dependen de la versión de vLLM y del largo de contexto):

BF16~16 GBreferenciareferencia
FP8_DYNAMIC~9 GB~1.3-1.5× más rápido~1.3-1.6× más tokens/s

Con batch chico la decodificación está limitada por el ancho de banda de memoria, así que menos bits por peso equivale a más velocidad; con mucha concurrencia pasa a dominar el cómputo y ahí ganan los formatos que cuantizan también las activaciones (FP8, NVFP4). La VRAM liberada se convierte en KV cache: más usuarios simultáneos con el mismo hardware.

9. Evaluar la calidad en español y portugués

La degradación por cuantización no es uniforme: tiende a concentrarse en idiomas y tareas menos representados, y la perplexity en inglés no la detecta. Medimos recovery (score de la variante / score BF16) en tasks es/pt de lm-eval. MGSM no incluye portugués, así que para pt usamos Global-MMLU-Lite y Belebele (para más tasks pt, ver la guía de evaluación).

bash · eval_all.sh (entorno 2)
#!/usr/bin/env bash

done
python · report.py (entorno 2)
import glob
import json

import pandas as pd

BASE = "Qwen3-8B"
VARIANTS = ["Qwen3-8B", "Qwen3-8B-FP8-dynamic", "Qwen3-8B-W4A16-gptq-es-pt",
            "Qwen3-8B-W4A16-gptq-default", "Qwen3-8B-W4A16-awq-es-pt"]
# Métrica principal por task (prefijo de la clave "métrica,filtro" de lm-eval)
PREFERRED = ["exact_match,flexible-extract", "acc,none", "prompt_level_strict_acc,none"]


def load_scores(name: str) -> dict[str, float]:
    files = sorted(glob.glob(f"results/{name}/**/results_*.json", recursive=True))
    results = json.load(open(files[-1], encoding="utf-8"))["results"]
    scores = {}
    for task, metrics in results.items():
        for key in PREFERRED:
            if key in metrics:
                scores[task] = float(metrics[key])
                break
    return scores


table = pd.DataFrame({v: load_scores(v) for v in VARIANTS})
recovery = table.div(table[BASE], axis=0) * 100
print("Scores:\n", table.round(4))
print("\nRecovery (% de BF16):\n", recovery.round(1))
print("\nRecovery medio:\n", recovery.mean().round(1))

# Criterio de aceptación sugerido: recovery medio >= 99% y ningún task < 97%
ok = (recovery.mean() >= 99) & (recovery.min() >= 97)
print("\nAprobados para producción:", list(ok[ok].index))
Qué mirar: compara gptq-es-pt contra gptq-default. Si la calibración es/pt sube el recovery en MGSM-es y Global-MMLU-pt aunque baje un poco en IFEval (inglés), confirmaste que conviene calibrar en el idioma de uso. Publica el checkpoint con una model card en español que incluya esta tabla por idioma: otras instituciones de la región podrán decidir si les sirve en sus GPUs.
No confíes en una sola métrica: diferencias menores a ~1 punto en benchmarks de cientos de ejemplos suelen estar dentro del ruido. Corre con varias semillas cuando la tarea es generativa y revisa a mano 20-30 respuestas largas en español: la cuantización agresiva suele notarse primero en coherencia y en mezcla de idiomas, no en multiple choice.

10. GGUF con llama.cpp (CPU, Mac, GPUs chicas)

GGUF es el formato de llama.cpp (repo ggml-org/llama.cpp) y de las herramientas que lo usan (Ollama, LM Studio). Corre en CPU, Apple Silicon (Metal), CUDA y Vulkan, con offloading parcial de capas a GPU. La importance matrix (imatrix) cumple el rol de la calibración: mide qué pesos importan más según activaciones reales, y conviene calcularla con texto es/pt.

Compilar, convertir y calcular la imatrix
bash
# Compilar (en Mac Metal se activa por defecto; para NVIDIA agrega -DGGML_CUDA=ON)
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release -j

11. Alternativas: GPTQModel y torchao

GPTQModel es el backend GPTQ de transformers (reemplaza a AutoGPTQ). Sirve si quieres cuantizar desde from_pretrained sin instalar llm-compressor; el checkpoint resultante también lo carga vLLM. Recibe la calibración como lista de textos más el tokenizer.

python · pip install optimum accelerate && pip install gptqmodel --no-build-isolation
from transformers import AutoModelForCausalLM, AutoTokenizer, GPTQConfig

MODEL_ID = "Qwen/Qwen3-8B"
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)

# Textos de calibración es/pt (por ejemplo, los bloques de calib_es_pt.txt)
with open("calib_es_pt.txt", encoding="utf-8") as f:
    calib_texts = [t for t in f.read().split("\n\n") if t.strip()][:256]

gptq_config = GPTQConfig(bits=4, group_size=128, dataset=calib_texts, tokenizer=tokenizer)

model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID, device_map="auto", quantization_config=gptq_config
)
model.save_pretrained("Qwen3-8B-gptqmodel-4bit")
tokenizer.save_pretrained("Qwen3-8B-gptqmodel-4bit")

torchao es la opción PyTorch-nativa (quantize_ con configs como Float8DynamicActivationFloat8WeightConfig), útil para experimentar dentro de PyTorch o con torch.compile, y es la misma librería que se usa para entrenar en FP8/MXFP8. Para servir en producción con vLLM, llm-compressor sigue siendo el camino con más cobertura de formatos y kernels.
