Reproducir una scaling law para es/pt

Decidir tamaño de modelo y cantidad de tokens para LatamGPT con evidencia propia: una grilla barata de 5 tamaños (22M-330M) con un solo run WSD por tamaño y cooldowns ramificados, ajuste tipo Chinchilla por IsoFLOPs y paramétrico con intervalos bootstrap, leyes separadas para español y portugués, predicción de tareas con model ladders y cómo pasar de la curva a una decisión con ATLAS y datos limitados.

1. Qué predice una scaling law (y qué no)

Una scaling law de pretraining modela la loss de validación de un modelo de N parámetros entrenado con D tokens. La forma de Chinchilla (Hoffmann et al., 2022) es L(N, D) = E + A/Nα + B/Dβ: E es la entropía irreducible del texto, y los otros dos términos son lo que se pierde por tener un modelo finito y datos finitos. Con el costo de entrenamiento aproximado como C ≈ 6·N·D FLOPs, minimizar L a C fijo da Nopt ∝ Cβ/(α+β) y Dopt ∝ Cα/(α+β). Si α ≈ β, ambos crecen como √C y la razón tokens/parámetro queda casi constante (los famosos ~20).

La consecuencia práctica: cuenta parámetros totales (con embedding y lm_head), usa warmup corto y proporcional al tamaño, y ajusta el LR por tamaño. Los modelos chicos de una grilla tienen una fracción enorme de parámetros en el embedding (con vocabulario de 32K, más de la mitad en el más chico de esta guía), así que el error de Kaplan aparece justo donde vamos a medir.

Lo que no predice: una ley ajustada a una mezcla de datos, un tokenizer y una arquitectura vale para esa combinación. Cambiar la proporción es/pt, el filtrado o el vocabulario cambia E, A y B. Tampoco dice nada directo sobre benchmarks: para eso está la sección 5. Y extrapolar de 330M a 30B son dos órdenes de magnitud: el resultado es un rango con incertidumbre, no un número.

2. Diseño barato: un run WSD por tamaño, cooldowns ramificados

Con el schedule coseno hay que fijar la duración antes de empezar, así que cada punto (N, D) cuesta un entrenamiento completo. Hägele et al. (2024) muestran que un LR constante con un cooldown corto al final escala de forma tan predecible como el coseno y permite ramificar: un solo run estable por tamaño, del que se sacan checkpoints, y desde cada checkpoint un cooldown lineal a cero que produce un modelo "terminado". Con cooldowns del 20% (lo que ellos usan para scaling laws) igualan al coseno; en su estimación tipo Chinchilla, reutilizar runs bajó el cómputo total a menos de la mitad.

Fase estable por tamaño (warmup = N tokens, LR constante)
→
Checkpoint al 80% de cada rama → cooldown lineal a 0
→
Loss es/pt en validación fija → IsoFLOP + ajuste paramétrico

Elegimos las ramas por presupuesto de cómputo (enfoque 2 de Chinchilla): para cada C en {1e17, 3e17, 1e18, 3e18, 1e19} y cada tamaño, la rama termina en D = C / 6N si eso da entre 2.5 y 400 tokens/parámetro. Así los presupuestos centrales quedan cubiertos por 3-4 tamaños a ambos lados del óptimo (los extremos tienen 2-3), y los mismos 16 puntos sirven para el ajuste paramétrico, que agradece razones D/N variadas (de ~5 a ~330). Los modelos chicos hacen las ramas largas (barato) y los grandes las cortas.

python
# grid.py — tamaños de la grilla (forma casi fija) y plan de cooldowns por presupuesto IsoFLOP
import math
from dataclasses import dataclass

VOCAB = 32_768
SEQ_LEN = 2048
HEAD_DIM = 64
BUDGETS = (1e17, 3e17, 1e18, 3e18, 1e19)         # FLOPs, convención Chinchilla C = 6·N·D
MIN_RATIO, MAX_RATIO = 2.5, 400                    # tokens por parámetro admitidos por rama
COOLDOWN_FRAC = 0.2                                # cooldown = 20% final de cada rama (Hägele et al.)
A100_FLOPS, MFU = 312e12, 0.40                     # bf16 denso; mide tu MFU real y ajusta


@dataclass
class GridPoint:
    name: str
    d_model: int
    n_layers: int
    n_heads: int
    n_kv_heads: int
    d_ff: int
    batch_seqs: int      # lote global en secuencias de SEQ_LEN
    lr: float            # punto de partida; confirmar con el mini-barrido de la sección 3
    beta2: float         # 0.99 con lotes chicos (Porian et al.), 0.95 en el resto
    n_params: int = 0    # totales: embedding (atado a lm_head) contado una vez
    flops_per_token: float = 0.0

    def __post_init__(self):
        attn = self.d_model * HEAD_DIM * (2 * self.n_heads + 2 * self.n_kv_heads) + 2 * HEAD_DIM
        per_layer = attn + 3 * self.d_model * self.d_ff + 2 * self.d_model
        self.n_params = self.n_layers * per_layer + self.d_model + VOCAB * self.d_model
        # 6N + atención causal (≈ 6·L·T·d_attn / 2); solo para estimar horas, no entra en el ajuste
        self.flops_per_token = 6 * self.n_params + 3 * self.n_layers * SEQ_LEN * self.n_heads * HEAD_DIM

    @property
    def tokens_per_step(self) -> int:
        return self.batch_seqs * SEQ_LEN

    @property
    def warmup_steps(self) -> int:
        return math.ceil(self.n_params / self.tokens_per_step)   # warmup = N tokens (Porian et al.)

    def branches(self) -> list[dict]:
        out = []
        for c in BUDGETS:
            tokens = c / (6 * self.n_params)
            if MIN_RATIO <= tokens / self.n_params <= MAX_RATIO:
                total = round(tokens / self.tokens_per_step)
                out.append({"budget": c, "ratio": round(tokens / self.n_params, 1),
                            "branch_step": round((1 - COOLDOWN_FRAC) * total), "total_steps": total})
        return out


def point(name, d, L, batch, lr, beta2):
    h = d // HEAD_DIM
    return GridPoint(name, d, L, h, max(1, h // 2), round(8 / 3 * d / 128) * 128, batch, lr, beta2)


GRID = {g.name: g for g in [
    point("s22m", 384, 6, 32, 3e-3, 0.99),
    point("s40m", 512, 8, 64, 3e-3, 0.99),
    point("s83m", 640, 14, 128, 2e-3, 0.99),
    point("s164m", 896, 15, 192, 1.5e-3, 0.95),
    point("s330m", 1152, 20, 256, 1e-3, 0.95),
]}

if __name__ == "__main__":
    total_h = 0.0
    for g in GRID.values():
        br = g.branches()
        stable = max(b["branch_step"] for b in br)
        steps = stable + sum(b["total_steps"] - b["branch_step"] for b in br)
        hours = steps * g.tokens_per_step * g.flops_per_token / (A100_FLOPS * MFU * 3600)
        total_h += hours
        print(f"{g.name:6s} N={g.n_params / 1e6:6.1f}M  ratios={[b['ratio'] for b in br]}  "
              f"pasos estables={stable:,}  ≈{hours:5.1f} A100-h")
    print(f"Total ≈ {total_h:.0f} A100-h")

Por qué estos números: la razón ancho/profundidad se mantiene entre ~45 y ~65 para que la forma no confunda el efecto del tamaño; el lote crece con N para que hasta la rama más corta tenga miles de pasos; el warmup dura N tokens, como en Porian et al. (con el warmup fijo de Kaplan, los modelos chicos llegaban a su óptimo de cómputo todavía en warmup); y β2 = 0.99 en los lotes chicos, otra de sus correcciones. Para el sanity check deja en BUDGETS solo 3e17 y 1e18, y en GRID los tres tamaños chicos.

3. Correr la grilla en SLURM con el código de "LLM desde cero"

Reutilizamos model.py y prepare_data.py de Un LLM moderno desde cero: mismo decoder (RMSNorm, RoPE, GQA, SwiGLU, QK-norm), mismo tokenizer es/pt de 32K y los mismos shards uint16 con validación separada val_es.bin y val_pt.bin. Solo hay que subir TRAIN_TOKENS a ~21B (unos 42 GB en disco) para que ninguna rama repita datos: la repetición es otra variable, y la tratamos aparte en la sección 6.

train_grid.py tiene dos modos. En stable entrena con warmup y LR constante, y guarda modelo y optimizador en el paso de ramificación de cada presupuesto. En cooldown carga ese checkpoint, decae el LR linealmente a cero con get_wsd_schedule y mide la loss en un conjunto fijo de 4M tokens por idioma. Los datos se leen en orden y sin repetición, así que el cooldown ve exactamente los tokens que el run estable habría visto a continuación.

python
# train_grid.py — fase estable (LR constante) o cooldown ramificado de un tamaño de la grilla
# uso: torchrun --standalone --nproc_per_node=1 train_grid.py --size s83m --mode stable
#      torchrun --standalone --nproc_per_node=1 train_grid.py --size s83m --mode cooldown --branch 2
import argparse
import json
import math
import os
from dataclasses import asdict
from pathlib import Path

import numpy as np
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from transformers import get_wsd_schedule

from grid import GRID, HEAD_DIM, SEQ_LEN
from model import LLM, ModelConfig          # model.py de la guía "LLM desde cero"

p = argparse.ArgumentParser()
p.add_argument("--size", required=True, choices=list(GRID))
p.add_argument("--mode", required=True, choices=["stable", "cooldown"])
p.add_argument("--branch", type=int, default=0)          # índice en GRID[size].branches()
p.add_argument("--max-branch", type=int, default=None)   # cortar la fase estable (mini-barrido de LR)
p.add_argument("--lr", type=float, default=None)
p.add_argument("--micro-batch", type=int, default=16)    # 8 en GPUs de 40 GB
p.add_argument("--out", default="sl_runs")
p.add_argument("--seed", type=int, default=0)
args = p.parse_args()

g = GRID[args.size]
branches = g.branches()
out = Path(args.out) / args.size
out.mkdir(parents=True, exist_ok=True)

ddp = int(os.environ.get("WORLD_SIZE", 1)) > 1
if ddp:
    dist.init_process_group("nccl")
rank, world = (dist.get_rank(), dist.get_world_size()) if ddp else (0, 1)
local_rank = int(os.environ.get("LOCAL_RANK", 0))
torch.cuda.set_device(local_rank)
device = f"cuda:{local_rank}"
torch.set_float32_matmul_precision("high")
assert g.batch_seqs % (args.micro_batch * world) == 0, "batch_seqs debe ser múltiplo de micro_batch × GPUs"
accum = g.batch_seqs // (args.micro_batch * world)

meta = json.loads(Path("data/meta.json").read_text())
train = np.memmap("data/train.bin", dtype=np.uint16, mode="r")
need = max(b["total_steps"] for b in branches) * g.tokens_per_step + 1
assert len(train) >= need, f"train.bin tiene {len(train):,} tokens y la rama más larga usa {need:,}"


def get_batch(step: int, micro: int):   # lectura secuencial sin repetición: el paso s siempre ve los mismos tokens
    seq0 = step * g.batch_seqs + (rank * accum + micro) * args.micro_batch
    start = seq0 * SEQ_LEN
    buf = torch.from_numpy(train[start:start + args.micro_batch * SEQ_LEN + 1].astype(np.int64))
    buf = buf.pin_memory().to(device, non_blocking=True)
    return buf[:-1].view(args.micro_batch, SEQ_LEN), buf[1:].view(args.micro_batch, SEQ_LEN)


@torch.no_grad()
def evaluate(model: LLM, n_tokens: int = 4_000_000) -> dict:   # mismo conjunto fijo para todos los puntos
    model.eval()
    res = {}
    for lang in ("es", "pt"):
        arr = np.memmap(f"data/val_{lang}.bin", dtype=np.uint16, mode="r")
        n_seq = min(n_tokens, len(arr) - 1) // SEQ_LEN
        total = 0.0
        for i in range(0, n_seq, args.micro_batch):
            b = min(args.micro_batch, n_seq - i)
            buf = torch.from_numpy(arr[i * SEQ_LEN:(i + b) * SEQ_LEN + 1].astype(np.int64)).to(device)
            with torch.autocast("cuda", dtype=torch.bfloat16):
                _, _, ce = model(buf[:-1].view(b, SEQ_LEN), buf[1:].view(b, SEQ_LEN))
            total += ce.item() * b
        res[f"loss_{lang}"] = total / n_seq
        res[f"bpb_{lang}"] = res[f"loss_{lang}"] / math.log(2) / meta[f"val_{lang}"]["bytes_per_token"]
    model.train()
    return res


cfg = ModelConfig(vocab_size=meta["vocab_size"], d_model=g.d_model, n_layers=g.n_layers,
                  n_heads=g.n_heads, n_kv_heads=g.n_kv_heads, head_dim=HEAD_DIM, d_ff=g.d_ff,
                  max_seq_len=SEQ_LEN)
torch.manual_seed(args.seed)
raw = LLM(cfg).to(device)
n_real = sum(prm.numel() for prm in raw.parameters())   # parameters() no duplica el peso atado
assert abs(n_real - g.n_params) / g.n_params < 0.01, (n_real, g.n_params)

decay, no_decay = [], []
for name, prm in raw.named_parameters():
    (decay if prm.dim() == 2 and "embed_tokens" not in name else no_decay).append(prm)
lr = args.lr or g.lr
opt = torch.optim.AdamW(
    [{"params": decay, "weight_decay": 0.1}, {"params": no_decay, "weight_decay": 0.0}],
    lr=lr, betas=(0.9, g.beta2), eps=1e-8, fused=True,
)

if args.mode == "stable":
    todo = branches if args.max_branch is None else branches[:args.max_branch + 1]
    ckpt_steps = {b["branch_step"] for b in todo}
    start, end = 0, max(ckpt_steps)
    # Warmup lineal de N tokens y después LR constante: la fase de decay nunca se alcanza
    sched = get_wsd_schedule(opt, num_warmup_steps=g.warmup_steps, num_decay_steps=0,
                             num_stable_steps=end)
else:
    br = branches[args.branch]
    ck = torch.load(out / f"stable_{br['branch_step']}.pt", map_location=device)
    raw.load_state_dict(ck["model"])
    opt.load_state_dict(ck["opt"])
    lr = ck["lr"]
    for group in opt.param_groups:
        group["lr"] = group["initial_lr"] = lr
    start, end = br["branch_step"], br["total_steps"]
    sched = get_wsd_schedule(opt, num_warmup_steps=0, num_decay_steps=end - start,
                             num_stable_steps=0, decay_type="linear", min_lr_ratio=0.0)

model = torch.compile(raw)
if ddp:
    model = DDP(model, device_ids=[local_rank])

for step in range(start, end):
    for micro in range(accum):
        x, y = get_batch(step, micro)
        if ddp:
            model.require_backward_grad_sync = micro == accum - 1   # sincroniza solo en el último
        with torch.autocast("cuda", dtype=torch.bfloat16):
            _, loss, _ = model(x, y)
        (loss / accum).backward()
    torch.nn.utils.clip_grad_norm_(raw.parameters(), 1.0)
    opt.step()
    sched.step()
    opt.zero_grad(set_to_none=True)
    if rank == 0 and step % 200 == 0:
        print(f"{args.size} {args.mode} paso {step}/{end} loss {loss.item():.3f} "
              f"lr {sched.get_last_lr()[0]:.2e}", flush=True)
    if args.mode == "stable" and rank == 0 and step + 1 in ckpt_steps:
        torch.save({"model": raw.state_dict(), "opt": opt.state_dict(), "cfg": asdict(cfg),
                    "lr": lr, "step": step + 1}, out / f"stable_{step + 1}.pt")

if args.mode == "cooldown" and rank == 0:
    tag = f"{br['budget']:.0e}"
    res = {"size": args.size, "seed": args.seed, "n_params": g.n_params, "budget": br["budget"], "ratio": br["ratio"],
           "tokens": end * g.tokens_per_step, "lr": lr, **evaluate(raw)}
    torch.save({"model": raw.state_dict(), "cfg": asdict(cfg), "step": end}, out / f"final_{tag}.pt")
    (out / f"cooldown_{tag}.json").write_text(json.dumps(res, indent=2))
if ddp:
    dist.destroy_process_group()

El lanzador encola, por tamaño, el run estable y un job array con sus cooldowns que arranca cuando el estable termina. Los tamaños grandes usan varias GPUs con DDP; el lote global no cambia, solo la acumulación.

bash
#!/usr/bin/env bash
# submit_grid.sh — fase estable por tamaño + array de cooldowns dependiente (SLURM)
set -euo pipefail
mkdir -p logs
declare -A GPUS=([s22m]=1 [s40m]=1 [s83m]=1 [s164m]=2 [s330m]=2)

for SIZE in s22m s40m s83m s164m s330m; do
  G=${GPUS[$SIZE]}
  LAST=$(python -c "from grid import GRID; print(len(GRID['$SIZE'].branches()) - 1)")
  COMMON=(--gpus-per-node="$G" --cpus-per-task=$((8 * G)) --time=2-00:00:00)
  JID=$(sbatch --parsable "${COMMON[@]}" --job-name="st-$SIZE" --output="logs/%x-%j.out" \
    --wrap="torchrun --standalone --nproc_per_node=$G train_grid.py --size $SIZE --mode stable")
  sbatch "${COMMON[@]}" --job-name="cd-$SIZE" --array="0-$LAST" --dependency="afterok:$JID" \
    --output="logs/%x-%A_%a.out" \
    --wrap="torchrun --standalone --nproc_per_node=$G train_grid.py --size $SIZE --mode cooldown --branch \$SLURM_ARRAY_TASK_ID"
done
Mini-barrido de LR por tamaño

El error más caro de una scaling law es comparar tamaños con LR mal elegido: el tamaño desfavorecido parece peor de lo que es y el exponente se tuerce (es una de las correcciones de Porian et al.). Antes de lanzar la grilla, barre ×0.5, ×1 y ×2 del LR de partida usando solo la rama más corta de cada tamaño, que es barata. Para cada LR: train_grid.py --mode stable --max-branch 0 --lr 2e-3 --out sweep/lr2e-3 y después --mode cooldown --branch 0 con el mismo --out; compara loss_es en los JSON resultantes. Si el mejor queda en un extremo, amplía el barrido. Si no tienes presupuesto para barrer todo, μP permite transferir el LR del modelo chico, pero exige cambiar la inicialización y el escalado por capa del modelo.

La loss durante la fase estable está inflada por el LR alto, y la caída del cooldown no es la misma para todos los tamaños: mezclar checkpoints estables con modelos terminados sesga el ajuste. Por la misma razón, la loss de validación sale siempre del mismo conjunto fijo de tokens y no de batches aleatorios.

4. Ajustar: IsoFLOPs y ley paramétrica con bootstrap

Enfoque 2 (IsoFLOP): dentro de cada presupuesto, la loss en función de log N tiene forma de valle. Una parábola da el Nopt de ese presupuesto, y una recta en log-log entre presupuestos da el exponente a. Es robusto porque no supone ninguna forma funcional, pero con 3-4 tamaños por presupuesto cada mínimo es ruidoso, y solo vale cuando el mínimo cae dentro de los tamaños medidos.

Enfoque 3 (paramétrico): ajusta E, A, B, α, β con todos los puntos a la vez. Seguimos la receta de Hoffmann et al. tal como la reconstruyen Besiroglu et al.: parametrizar log L̂ = LSE(a − α·log N, b − β·log D, e) con A = ea, B = eb y E = ee; usar pérdida de Huber con δ = 10-3 sobre los residuos en log; probar una grilla de inicializaciones; y sumar la pérdida en vez de promediarla. Besiroglu et al. señalan que promediarla deja la pérdida en una escala tan chica que el optimizador termina antes de tiempo. Los intervalos salen de un bootstrap sobre los puntos.

python
# fit_scaling.py — IsoFLOP (enfoque 2) + ajuste paramétrico con bootstrap (enfoque 3)
# uso: python fit_scaling.py --target-flops 1e23 --lang es
import argparse
import itertools

import numpy as np
import pandas as pd
from scipy.optimize import minimize
from scipy.special import huber, logsumexp

p = argparse.ArgumentParser()
p.add_argument("--results", default="results.csv")
p.add_argument("--lang", choices=["es", "pt"], default="es")
p.add_argument("--target-flops", type=float, default=1e23)
p.add_argument("--n-boot", type=int, default=1000)
args = p.parse_args()

df = pd.read_csv(args.results)
N = df["n_params"].to_numpy(float)
D = df["tokens"].to_numpy(float)
L = df[f"loss_{args.lang}"].to_numpy(float)

# ---------- (a) IsoFLOP: dentro de cada presupuesto, parábola de la loss en log N ----------
iso = []
for c, g in df.groupby("budget"):
    if len(g) < 3:
        continue                                  # con menos de 3 tamaños no hay parábola
    a2, a1, _ = np.polyfit(np.log(g["n_params"]), g[f"loss_{args.lang}"], 2)
    n_opt = np.exp(-a1 / (2 * a2))
    if a2 > 0 and g["n_params"].min() < n_opt < g["n_params"].max():   # mínimo real y medido
        iso.append((c, n_opt, c / (6 * n_opt), len(g)))
iso = pd.DataFrame(iso, columns=["C", "N_opt", "D_opt", "n_sizes"])
print(iso.to_string(index=False, float_format="%.3g"))
if len(iso) >= 2:
    a_iso = np.polyfit(np.log(iso["C"]), np.log(iso["N_opt"]), 1)[0]
    print(f"IsoFLOP: N_opt ∝ C^{a_iso:.3f}   D_opt ∝ C^{1 - a_iso:.3f}")

# ---------- (b) Paramétrico: log L = LSE(a - α log N, b - β log D, e) ----------
logN, logD, logL = np.log(N), np.log(D), np.log(L)


def objective(theta, idx, delta=1e-3):
    """Σ Huber(log L̂ − log L) y su gradiente analítico (con jac, L-BFGS-B es mucho más rápido)."""
    a, b, e, alpha, beta = theta
    lnN, lnD = logN[idx], logD[idx]
    u = np.stack([a - alpha * lnN, b - beta * lnD, np.full(len(idx), e)])
    pred = logsumexp(u, axis=0)
    r = pred - logL[idx]
    w = np.exp(u - pred)                                 # softmax: ∂pred/∂u
    dr = np.clip(r, -delta, delta)                       # derivada de la pérdida de Huber
    grad = np.array([dr @ w[0], dr @ w[1], dr @ w[2], -dr @ (w[0] * lnN), -dr @ (w[1] * lnD)])
    return huber(delta, r).sum(), grad                   # suma, no media: con la media L-BFGS corta antes


def fit(idx, inits):
    best = None
    for x0 in inits:
        r = minimize(objective, x0, args=(idx,), jac=True, method="L-BFGS-B",
                     bounds=[(None, None)] * 3 + [(0.0, 2.0)] * 2,
                     options={"ftol": 1e-14, "gtol": 1e-12, "maxiter": 5000})   # la pérdida es ~1e-4: tolerancias finas
        if best is None or r.fun < best.fun:
            best = r
    return best.x


# Grilla de inicializaciones (a, b, e, α, β): el óptimo de L-BFGS depende mucho del punto de partida
grid = list(itertools.product(range(0, 26, 5), range(0, 26, 5), (-1.0, 0.0, 1.0),
                              (0.2, 0.5, 1.0), (0.2, 0.5, 1.0)))
all_idx = np.arange(len(df))
theta = fit(all_idx, grid)


def compute_optimal(theta, c):
    a, b, e, alpha, beta = theta
    A, B, E = np.exp(a), np.exp(b), np.exp(e)
    G = (alpha * A / (beta * B)) ** (1 / (alpha + beta))
    n_opt = G * (c / 6) ** (beta / (alpha + beta))
    return n_opt, (c / 6) / n_opt, E


rng = np.random.default_rng(0)
boot = []
for _ in range(args.n_boot):
    idx = rng.choice(all_idx, size=len(all_idx), replace=True)
    boot.append(fit(idx, [theta]))                # el bootstrap parte del óptimo, no de la grilla
boot = np.array(boot)

a, b, e, alpha, beta = theta
print(f"\nE={np.exp(e):.3f}  A={np.exp(a):.1f}  B={np.exp(b):.1f}  α={alpha:.3f}  β={beta:.3f}")
lo, hi = np.percentile(boot[:, 3:], [2.5, 97.5], axis=0)
print(f"IC 95%: α ∈ [{lo[0]:.3f}, {hi[0]:.3f}]  β ∈ [{lo[1]:.3f}, {hi[1]:.3f}]")
a_param = beta / (alpha + beta)
a_boot = boot[:, 4] / (boot[:, 3] + boot[:, 4])
print(f"N_opt ∝ C^{a_param:.3f}  (IC 95% [{np.percentile(a_boot, 2.5):.3f}, {np.percentile(a_boot, 97.5):.3f}])")

n_opt, d_opt, _ = compute_optimal(theta, args.target_flops)
bo = np.array([compute_optimal(t, args.target_flops)[:2] for t in boot])
(n_lo, d_lo), (n_hi, d_hi) = np.percentile(bo, [2.5, 97.5], axis=0)
print(f"\nC = {args.target_flops:.1e} FLOPs ({args.lang}):")
print(f"  N_opt = {n_opt / 1e9:.2f}B  (IC 95% {n_lo / 1e9:.2f}-{n_hi / 1e9:.2f}B)")
print(f"  D_opt = {d_opt / 1e9:.0f}B tokens  (IC 95% {d_lo / 1e9:.0f}-{d_hi / 1e9:.0f}B)  "
      f"→ {d_opt / n_opt:.0f} tokens/parámetro")

Con 16 puntos (32 con dos semillas) el ajuste completo (grilla de 972 inicializaciones más 1000 remuestreos) tarda del orden de 10-20 minutos en una CPU. Corre ambos idiomas: --lang es y --lang pt.

Cómo leer tu salida: como referencia en inglés (MassiveText), la réplica de Besiroglu et al. obtiene E = 1.82, A = 482.0, B = 2085.4, α = 0.348 y β = 0.366 (~20 tokens/parámetro), mientras que los valores publicados por Hoffmann et al. (E = 1.69, A = 406.4, B = 410.7, α = 0.34, β = 0.28) implican ~70, inconsistentes con sus propios ~20. No compares tus E, A y B con esos valores, porque dependen del tokenizer (nats por token de un BPE es/pt de 32K no son los de MassiveText). Lo comparable es el exponente a = β/(α+β) y la razón tokens/parámetro en el óptimo. Si el IsoFLOP y el paramétrico difieren mucho, o el intervalo de a cruza 0.4-0.6 de punta a punta, la grilla no alcanza: agrega un tamaño intermedio o semillas. Choshen et al. (2024) muestran que la variabilidad entre semillas es grande y que a veces rinde más entrenar varios modelos chicos que uno grande.
Tres trampas del ajuste: (1) intervalos estrechísimos suelen indicar que el optimizador no se movió: revisa las tolerancias (la pérdida vale ~10-4) y que el bootstrap realmente cambie θ; (2) α y A están muy correlacionados, y también β y B, así que los parámetros sueltos tienen intervalos amplios aunque a esté bien determinado; (3) si al quitar un tamaño el exponente salta más que su intervalo, el bootstrap sobre puntos subestima la incertidumbre. Remuestrear por tamaño en vez de por punto es una variante más conservadora. Para fundamentos de bootstrap e intervalos, ver Evaluación estadística.

5. De loss a tareas: model ladder en dos pasos

La loss de validación no es lo que reporta un paper de modelo. Bhagia et al. (2024) predicen la accuracy por tarea de modelos de 7B y 13B en dos pasos: (N, D) → loss de la respuesta correcta → accuracy, con una ley tipo Chinchilla para el primer paso y una sigmoide para el segundo. Con modelos ladder que costaron ~1% del cómputo de los objetivos, el error absoluto quedó dentro de 2 puntos en cuatro tareas de opción múltiple.

A la escala de esta grilla hay que elegir bien la tarea. Con 4 opciones, Belebele suele quedar cerca del azar (25%) en modelos de este tamaño, así que el paso 2 tendría poca señal; XStoryCloze en español (2 opciones) sí se separa del 50% con modelos chicos. Aun así, el paso 1 (la loss de la respuesta correcta) es útil en ambas: es continuo y baja de forma predecible aunque la accuracy todavía esté plana. Exporta cada modelo terminado a formato Qwen3 con export_hf.py de la guía base (cambiando su ruta de entrada y de salida por sys.argv[1] y sys.argv[2]) y evalúa con lm-eval guardando las muestras.

python
# predict_tasks.py — ladder de dos pasos: (N, D) → NLL de la respuesta correcta → accuracy
import glob
import json

import numpy as np
import pandas as pd
from scipy.optimize import curve_fit
from scipy.special import expit

TASK, CHANCE = "xstorycloze_es", 0.5
TARGET_N, TARGET_D = 8e9, 2e12          # el modelo que quieres predecir


def task_stats(run_dir: str, task: str) -> tuple[float, float]:
    path = sorted(glob.glob(f"{run_dir}/**/samples_{task}_*.jsonl", recursive=True))[-1]
    nll, acc = [], []
    with open(path, encoding="utf-8") as f:
        for line in f:
            s = json.loads(line)
            lls = [float(r[0]) for r in s["filtered_resps"]]   # (loglik, is_greedy) por opción
            gold = int(s["target"])
            nll.append(-lls[gold])
            acc.append(float(np.argmax(lls) == gold))
    return float(np.mean(nll)), float(np.mean(acc))


res = pd.read_csv("results.csv").query("seed == 0")   # eval_ladder.sh evalúa solo la semilla 0
stats = [task_stats(f"evals/{r.size}_{r.budget:.0e}", TASK) for r in res.itertuples()]
res["task_nll"], res["task_acc"] = zip(*stats)
N, D = res["n_params"].to_numpy(float), res["tokens"].to_numpy(float)


def step1(X, E, A, alpha, B, beta):
    n, d = X
    return E + A / n**alpha + B / d**beta


def step2(x, a, x0, k, b):
    return a * expit(k * (x - x0)) + b      # sigmoide (estable numéricamente); decrece en la loss si a < 0


p1, _ = curve_fit(step1, (N, D), res["task_nll"], p0=[0.5, 50, 0.3, 50, 0.3],
                  bounds=([0, 0, 0, 0, 0], [10, 1e6, 2, 1e6, 2]), maxfev=20_000)
p2, _ = curve_fit(step2, res["task_nll"], res["task_acc"],
                  p0=[-(1 - CHANCE), res["task_nll"].median(), 5.0, 1.0], maxfev=20_000)

nll_hat = step1((np.array([TARGET_N]), np.array([TARGET_D])), *p1)[0]
acc_hat = step2(nll_hat, *p2)
print(f"{TASK}: NLL predicha {nll_hat:.3f} (mínima medida {res['task_nll'].min():.3f})")
print(f"accuracy predicha {acc_hat:.3f}  · accuracy máxima en la ladder {res['task_acc'].max():.3f}")   # si está ~CHANCE, el paso 2 no sirve
Variantes: Bhagia et al. normalizan la loss de la respuesta según la tarea; aquí usamos la NLL media sin normalizar, lo que basta para una sola tarea con respuestas de largo parecido. Gadre et al. (2024) proponen otra vía, que es ajustar una ley entre la perplejidad y el error top-1 promedio de un conjunto de tareas. Con ~1500 ejemplos, una accuracy de XStoryCloze tiene un error estándar de ~1.3 puntos, así que diferencias de 1-2 puntos entre predicción y medición son ruido.

6. Español, portugués y la mezcla: qué cambia

Ajusta dos leyes, una con loss_es y otra con loss_pt. Ambas comparten N y D totales con una mezcla 80/20 fija, así que la ley de portugués describe cómo mejora el portugués cuando ve el 20% de los tokens. Si los exponentes coinciden y solo cambia la loss, la mezcla está bien calibrada; si el portugués tiene un β claramente menor, está limitado por datos y conviene subir su proporción. Para decidir proporciones sin reentrenar la grilla para cada mezcla:

  • He et al. (2024): en más de 100 modelos y 23 idiomas, la loss de cada familia lingüística depende casi solo de su propia proporción de muestreo, y las proporciones óptimas halladas a 85M transfieren a 1.2B. Español y portugués son de la misma familia: basta barrer la proporción es+pt vs el resto con la grilla chica.
  • ATLAS (Longpre et al., 2025): 774 entrenamientos de 10M a 8B y más de 400 idiomas. La ley separa los tokens del idioma objetivo, los de 3 idiomas de transferencia (con pesos inicializados desde una matriz de transferencia 38×38, en la que español, catalán y portugués aparecen como grupo con transferencia positiva notable) y el resto, e incluye una función de saturación para tokens repetidos. Su ley de la "maldición del multilingüismo" estima que, para cuadruplicar los idiomas sin perder calidad, el modelo crece ~1.4× y los datos totales ~2.7×.
  • Desde cero vs continuar: ATLAS estima para un modelo de 2B que continuar desde un checkpoint multilingüe conviene por debajo de ~144B tokens y entrenar desde cero rinde más desde ~283B, con un cruce que depende del idioma. Si tu presupuesto cae en la zona de continuar, sigue con Mid-training y Continual pretraining.
Datos limitados: cuántas épocas tolera es/pt

El texto es/pt de alta calidad se termina antes que el inglés. Muennighoff et al. (2023), con 400 entrenamientos de hasta 9B parámetros y 900B tokens, encuentran que hasta ~4 épocas sobre los mismos datos cambian la loss de forma despreciable frente a datos únicos; más allá, el valor de cada token repetido decae hasta volverse nulo. Regla práctica: si Dopt × proporción es/pt supera ~4× tus tokens únicos de calidad, estás limitado por datos. Las salidas son mezclar más inglés y código (con transferencia estimada vía ATLAS), relajar el filtrado o entrenar un modelo más chico. Para verificarlo con tu propia ley, agrega a la grilla unas pocas ramas sobre un train.bin truncado (2 y 4 épocas) y compáralas con las de datos únicos.

7. De la curva a la decisión: tamaño y tokens para LatamGPT

Ejemplo ilustrativo con la ley de Besiroglu et al. (inglés): con C = 1023 FLOPs, del orden de 128 H100 durante ~23 días a 40% de MFU, el óptimo es N ≈ 29B y D ≈ 570B tokens (~19 tokens/parámetro). Pero el óptimo de entrenamiento casi nunca es el óptimo del proyecto:

Opción con el mismo C = 1e23Tokens/parámetroLoss predichaLectura
29B × 570B tokens~192.032Óptimo de entrenamiento; caro de servir y necesita 570B tokens
14B × 1.2T~852.040+0.4% de loss, la mitad del costo de inferencia
8B × 2.1T~2602.055+1.1% de loss, ~3.6× más barato de servir; necesita 2T tokens
3B × 5.6T~18502.106Fuera del rango ajustado: no confíes en la extrapolación

Sardana et al. (2023) formalizan el compromiso: con una demanda de inferencia del orden de mil millones de requests, conviene entrenar modelos más chicos por más tiempo. Además observan que ajustar solo con razones típicas de tokens/parámetro sobreestima el beneficio de seguir agregando tokens en razones extremas. Gadre et al. (2024) muestran que se puede extrapolar en el régimen sobreentrenado: predijeron la loss de un 1.4B con 900B tokens (32× sobreentrenado) usando 300× menos cómputo. Por eso la grilla incluye ramas de hasta ~330 tokens/parámetro, y por eso la decisión de LatamGPT sale de cruzar tres curvas: la ley es/pt propia, los tokens únicos disponibles (con ≤4 épocas) y el costo de servir.
